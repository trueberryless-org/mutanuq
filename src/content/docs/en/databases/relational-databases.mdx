The **relational model** was introduced by Edgar F. Codd at IBM in 1970. It stores all data in tables and links them only through values, not through pointers. Older hierarchical and network databases required programs to know the physical access paths. In the relational model, by contrast, a query only describes **which** data is wanted, and the database system decides by itself **how** to find it. This separation is the reason why relational databases have been the standard for structured data for more than 50 years.

## Terms

| Formal term      | Informal term             | Meaning                                                      |
| ---------------- | ------------------------- | ------------------------------------------------------------ |
| **Relation**     | table                     | set of tuples with the same attributes                       |
| **Tuple**        | row, record               | a single entry, for example one student                      |
| **Attribute**    | column, field             | a property with a name and a data type                       |
| **Domain**       | range of values, data type | the allowed values of an attribute, such as whole numbers from 1 to 5 |
| **Degree**       | number of columns         | number of attributes of a relation                           |
| **Cardinality**  | number of rows            | number of tuples of a relation                               |
| **Relation schema** | table structure        | name and attributes, for example `Student(Id, FirstName, LastName, ClassId)` |

An **entity** is a uniquely identifiable object of the real world about which data is stored. Entities of the same kind form an **entity type**, which is represented as a table. How to get from the design to tables is shown on the page [Data Modelling](/en/databases/data-modelling/).

### Properties of a relation

Because a relation is mathematically a **set**, the following rules apply:

- There are **no two identical tuples**. Every row must differ by a key.
- The **order of the rows** has no meaning. You only get a particular sort order with `ORDER BY`.
- The **order of the columns** has no meaning. Columns are addressed by their name.
- Every value is **atomic**, that is, it cannot be split further (see [first normal form](/en/databases/normalisation/#first-normal-form-1nf)).

SQL tables deviate from this in one point: without a primary key, they allow duplicate rows. Strictly speaking, they are **multisets**.

## Keys

Keys identify records and link tables with each other.

- **Superkey:** any set of attributes that uniquely identifies a record.
- **Candidate key:** a minimal superkey. You cannot leave out any attribute without losing uniqueness. A table can have several candidate keys, such as `Id` and `SocialSecurityNumber`.
- **Primary key** (`PRIMARY KEY`): the chosen candidate key. It must not be `NULL` and should never change.
- **Alternate key:** the remaining candidate keys. They are secured with `UNIQUE`.
- **Artificial key** (surrogate key): a key introduced specifically for this purpose without any business meaning, for example a sequential number or a GUID. In contrast, a **natural key** has a business meaning, such as the ISBN of a book.
- **Composite key:** a primary key made of several columns, typical for junction tables.
- **Foreign key** (`FOREIGN KEY`): a column that refers to the primary key (or an alternate key) of another table.

```sql
CREATE TABLE Class (
    Id   INT PRIMARY KEY,
    Name VARCHAR(10) NOT NULL UNIQUE
);

CREATE TABLE Student (
    Id        INT PRIMARY KEY,
    FirstName VARCHAR(50) NOT NULL,
    LastName  VARCHAR(50) NOT NULL,
    ClassId   INT REFERENCES Class(Id)
);
```

## Integrity constraints

Integrity constraints are rules that the database system checks on every change. A change that violates a rule is rejected. As a result, no program, not even a faulty one, can store invalid data.

| Integrity                    | Rule                                                                                   | Implementation in SQL              |
| ---------------------------- | -------------------------------------------------------------------------------------- | ---------------------------------- |
| **Entity integrity**         | Every row has a unique primary key that is not `NULL`.                                 | `PRIMARY KEY`                      |
| **Referential integrity**    | Every foreign key value refers to an existing row or is `NULL`.                        | `FOREIGN KEY ... REFERENCES`       |
| **Domain integrity**         | Every value lies within the allowed range of values.                                   | data type, `NOT NULL`, `CHECK`     |
| **User-defined integrity**   | business rules that cannot be expressed as a simple constraint                         | [triggers](/en/databases/sql-advanced/#triggers), procedures |

What happens when a referenced record is deleted or changed is determined by the **referential action**:

| Action          | Effect on dependent rows                                            |
| --------------- | ------------------------------------------------------------------- |
| `NO ACTION` / `RESTRICT` | The change is rejected (default).                          |
| `CASCADE`       | Dependent rows are deleted or changed as well.                      |
| `SET NULL`      | The foreign key is set to `NULL`.                                   |
| `SET DEFAULT`   | The foreign key is set to its default value.                        |

```sql
CREATE TABLE Absence (
    Id        INT PRIMARY KEY,
    StudentId INT NOT NULL REFERENCES Student(Id) ON DELETE CASCADE,
    Date      DATE NOT NULL,
    Lessons   INT NOT NULL CHECK (Lessons > 0)
);
```

If a student is deleted here, the database also deletes all of their absences. The page [Database Schema](/en/databases/schema/) describes all constraints in detail.

### NULL

`NULL` means "no value known" and is neither 0 nor an empty string. Every comparison with `NULL` results in neither true nor false, but **unknown**. That is why `WHERE ClassId = NULL` never returns a row; the correct form is `WHERE ClassId IS NULL`. The effects of this **three-valued logic** are described on the page [SQL Queries](/en/databases/sql-queries/#null-and-three-valued-logic).

## Structure of a database system

A **database system** (DBS) consists of the **database** (the stored data) and the **database management system** (DBMS, the software that manages it). A DBMS takes over tasks that every program would otherwise have to solve by itself:

| Component                       | Task                                                                                         |
| ------------------------------- | -------------------------------------------------------------------------------------------- |
| **Query processor**             | checks SQL statements for syntax and permissions and translates them into an execution plan  |
| **Query optimiser**             | chooses the cheapest among many equivalent plans, for example whether an [index](/en/databases/sql-advanced/#indexes) is used |
| **Transaction manager**         | ensures [ACID](/en/databases/transactions/#acid) and controls concurrent access through locks or versions |
| **Buffer manager**              | keeps frequently needed pages in main memory                                                 |
| **Storage manager**             | stores tables and indexes in files on disk                                                   |
| **Recovery component**          | restores a consistent state after a crash using the transaction log                          |
| **Catalogue** (data dictionary) | stores the metadata: which tables, columns, indexes and users exist                          |

The metadata can itself be queried with SQL, for example through the standardised views in `information_schema`:

```sql
SELECT table_name, column_name, data_type
FROM information_schema.columns
WHERE table_name = 'student'
ORDER BY ordinal_position;
```

PostgreSQL converts names that are not in double quotes to lower case, which is why `'student'` is written here.

### Codd's rules

In 1985, Codd published twelve rules (numbered from 0 to 12, so actually thirteen) that a system must meet to be considered relational. The most important ideas:

- All information, including the metadata, is represented as values in tables.
- Every value can be reached through the table name, column name and primary key.
- `NULL` is treated systematically and independently of the data type.
- A comprehensive language covers definition, querying, changes, permissions and transactions.
- Physical and logical **data independence**: applications do not have to be changed when the storage or the table structure changes (see [schema levels](/en/databases/schema/#schema-levels)).

No widely used product meets all rules completely, but they still serve as a yardstick today.

## SQL

**SQL** (_Structured Query Language_) is the language of relational databases. It was developed at IBM in the 1970s and has been standardised by ANSI since 1986 and by ISO since 1987 (ISO/IEC 9075). The current edition is SQL:2023. SQL is **declarative**: you describe the desired result, not the way to get there. The statements are divided into groups:

| Group                                     | Statements                                | Page                                                       |
| ----------------------------------------- | ----------------------------------------- | ---------------------------------------------------------- |
| **DDL** (_Data Definition Language_)      | `CREATE`, `ALTER`, `DROP`, `TRUNCATE`     | [SQL: Defining and Changing Data](/en/databases/sql-ddl-dml/) |
| **DML** (_Data Manipulation Language_)    | `INSERT`, `UPDATE`, `DELETE`, `MERGE`     | [SQL: Defining and Changing Data](/en/databases/sql-ddl-dml/) |
| **DQL** (_Data Query Language_)           | `SELECT`                                  | [SQL Queries](/en/databases/sql-queries/)                  |
| **DCL** (_Data Control Language_)         | `GRANT`, `REVOKE`                         | [Database Security](/en/databases/database-security/)      |
| **TCL** (_Transaction Control Language_)  | `BEGIN`, `COMMIT`, `ROLLBACK`, `SAVEPOINT` | [Transactions](/en/databases/transactions/)               |

DQL is often counted as part of DML. The theoretical foundation of `SELECT` is [relational algebra](/en/databases/relational-algebra/).

## Advantages and disadvantages

| Advantages                                                                                 | Disadvantages                                                                                    |
| ------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------ |
| simple, mathematically founded data model                                                  | rigid schema: structural changes to large tables are costly                                      |
| little redundancy through [normalisation](/en/databases/normalisation/)                    | related data is spread over many tables and has to be put together with joins                    |
| high consistency through constraints and [transactions](/en/databases/transactions/)       | horizontal scaling across many servers is difficult because joins and transactions across server boundaries are expensive |
| standardised, powerful query language SQL                                                  | hierarchical or highly connected data (trees, graphs) fits poorly into tables                    |
| mature products, tools and a lot of expertise                                              | objects in the program and tables do not match directly (_object-relational impedance mismatch_), which ORMs such as [Entity Framework](/en/databases/database-access/#entity-framework-core) compensate for |

For very large, distributed or weakly structured data, there are therefore [NoSQL databases](/en/databases/nosql/). In most business applications, however, a relational database is the right first choice.

## Products

| Product                  | Licence                     | Special features                                                                                 |
| ------------------------ | --------------------------- | ------------------------------------------------------------------------------------------------ |
| **PostgreSQL**           | open source (PostgreSQL licence) | very standards-compliant, object-relational, many data types (JSON, arrays, geodata with PostGIS), extensible |
| **MySQL**                | open source (GPL) and commercial, owned by Oracle | widely used in web applications, part of the LAMP stack (Linux, Apache, MySQL, PHP) |
| **MariaDB**              | open source (GPL)           | fork split off in 2009 by MySQL founder Michael Widenius, largely compatible with MySQL          |
| **Microsoft SQL Server** | commercial, free Express and Developer editions | SQL dialect T-SQL, very good integration with .NET and Entity Framework           |
| **Oracle Database**      | commercial                  | widespread in large companies, procedural extension PL/SQL                                       |
| **SQLite**               | public domain               | embedded library without a server, the whole database in one file, in every smartphone and browser |
| **IBM Db2**              | commercial                  | successor of the first SQL system, mainly on mainframes                                          |

The examples on these pages use PostgreSQL syntax, which is very close to the standard. Deviations of the other systems are mentioned where they occur frequently.
