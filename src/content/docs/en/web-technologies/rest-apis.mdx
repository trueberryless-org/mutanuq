A **web API** (_application programming interface_) provides data and functions over HTTP to other programs: to an SPA frontend, a mobile app or another server. Instead of HTML it returns data, usually as JSON. The most widespread architectural style for such interfaces is **REST**.

## REST principles

**REST** (_Representational State Transfer_) was described in 2000 by Roy Fielding, one of the authors of the HTTP specification, in his doctoral dissertation. REST is neither a protocol nor a standard but an architectural style with six **constraints**:

| Constraint              | Meaning                                                                                   |
| ----------------------- | ----------------------------------------------------------------------------------------- |
| **Client-server**       | user interface and data storage are separated and evolve independently                     |
| **Statelessness**       | every request contains all the necessary information (including authentication). The server stores no session state for the client, so any request can be handled by any server, which makes scaling easier |
| **Cacheability**        | responses state whether and for how long they may be cached                               |
| **Uniform interface**   | resources are identified by URIs and manipulated through **representations** (for example JSON), messages are self-descriptive (method, status code, `Content-Type`), and responses contain links to possible next steps (**HATEOAS**, _Hypermedia as the Engine of Application State_) |
| **Layered system**      | proxies, load balancers and caches can sit between client and server without the client noticing |
| **Code on demand** (optional) | the server can deliver executable code, for example JavaScript                      |

In practice almost any JSON API over HTTP is called "RESTful", even if it does not implement HATEOAS. The **Richardson Maturity Model** classifies APIs into levels: level 0 sends everything to one URL (like SOAP), level 1 introduces resources with their own URIs, level 2 also uses HTTP methods and status codes correctly, and level 3 adds hypermedia links. Most good APIs are at level 2.

## Resources and URIs

A **resource** is anything that deserves a name: a student, a class, a list of grades. Every resource has a **URI**. Good URIs are stable, predictable and describe **things, not actions**: what is done is stated by the HTTP method.

| good                                  | bad                              | Reason                                 |
| ------------------------------------- | -------------------------------- | -------------------------------------- |
| `GET /students`                       | `GET /getAllStudents`            | the verb belongs in the method          |
| `POST /students`                      | `POST /students/create`          | likewise                                |
| `GET /students/17`                    | `GET /students?id=17`            | a single resource as a path segment     |
| `GET /classes/3AHIT/students`         | `GET /studentsOfClass/3AHIT`     | express hierarchy in the path           |
| `GET /students?class=3AHIT&sort=name` | `GET /students/filter/3AHIT/name` | filtering, sorting, searching via the query |

Common conventions: **plural** nouns for collections, lower case with hyphens (`/exam-dates`), no file extensions (`.json`); the format is negotiated via `Accept` and `Content-Type`. Actions that cannot be represented as a resource are often modelled as a sub-resource: `POST /orders/42/cancellation`.

## HTTP methods and CRUD

The four basic operations on data (**CRUD**: _create, read, update, delete_) map directly onto the [HTTP methods](/en/web-technologies/http/#methods):

| Operation             | Method and URI          | Success                               | typical errors           |
| --------------------- | ----------------------- | ------------------------------------- | ------------------------ |
| read all              | `GET /students`         | `200 OK` with a list (possibly empty) |                          |
| read one              | `GET /students/17`      | `200 OK` with the object               | `404 Not Found`          |
| **c**reate            | `POST /students`        | `201 Created`, header `Location: /students/17`, body with the new object | `400 Bad Request`, `409 Conflict` |
| replace (**u**pdate)  | `PUT /students/17`      | `200 OK` with the object or `204 No Content` | `400`, `404`      |
| modify partially      | `PATCH /students/17`    | `200 OK`                               | `400`, `404`             |
| **d**elete            | `DELETE /students/17`   | `204 No Content`                       | `404`                    |

For all endpoints, add `401` (not logged in), `403` (not permitted) and `500` (server error). An empty search result is not an error but an empty list with `200`.

## JSON and error messages

Requests and responses use `Content-Type: application/json`. Property names in **camelCase** are common, dates as ISO 8601 strings (`"2026-09-07T08:00:00Z"`) and amounts of money as integers in cents or as strings, never as floating-point numbers.

Errors should provide not only a status code but also a machine-readable description. The **Problem Details** format (RFC 9457, `Content-Type: application/problem+json`) is standardised for this, and ASP.NET Core uses it out of the box:

```json
{
  "type": "https://tools.ietf.org/html/rfc9110#section-15.5.1",
  "title": "One or more validation errors occurred.",
  "status": 400,
  "errors": {
    "Name": ["The name must not be empty."]
  }
}
```

Stack traces and internal error messages do not belong in responses to clients, because they reveal details about the system to attackers.

## Versioning

A published API is used by programs that you do not control. Incompatible changes (renaming or removing a field, changing a type) must therefore not simply be rolled out. Compatible changes (a new optional field, a new endpoint), on the other hand, are allowed if clients ignore unknown fields.

| Variant           | Example                                      |
| ----------------- | -------------------------------------------- |
| in the path (most common) | `/api/v1/students`, `/api/v2/students` |
| as a query parameter | `/api/students?api-version=2`             |
| as a header       | `Api-Version: 2`                              |
| via the media type | `Accept: application/vnd.school.v2+json`     |

Old versions are operated in parallel for a while and only switched off after an announcement.

## Pagination

A collection with 100,000 entries is not delivered all at once. **Pagination** divides it into pages:

- **Offset-based**: `GET /students?page=3&pageSize=20` or `?offset=40&limit=20`. Simple, and you can jump directly to page 3. With large offsets the database query becomes slow, and if entries are inserted in the meantime, the pages shift.
- **Cursor-based**: `GET /students?after=eyJpZCI6NDB9&limit=20`. With every page the server returns an opaque cursor pointing to the last entry. Stable and fast, but no jumping to arbitrary pages.

The response contains the entries and metadata, for example the total count and links to the next page (in the body or in the `Link` header):

```json
{
  "items": [{ "id": 41, "name": "Anna Huber", "schoolClass": "3AHIT" }],
  "page": 3,
  "pageSize": 20,
  "totalCount": 512,
  "next": "/api/students?page=4&pageSize=20"
}
```

## OpenAPI and Swagger

**OpenAPI** is a standard for describing REST APIs in a machine-readable way in JSON or YAML: endpoints, parameters, data types of requests and responses, status codes and authentication. It emerged from the **Swagger** specification in 2015 and is developed by the OpenAPI Initiative of the Linux Foundation (version 3.1 since 2021, 3.2 since 2025). The name Swagger lives on in tools: **Swagger UI** generates an interactive documentation page from the description, on which endpoints can be tried out directly.

```yaml
openapi: 3.1.0
info:
  title: School API
  version: 1.0.0
paths:
  /api/students/{id}:
    get:
      summary: Retrieve a student
      parameters:
        - name: id
          in: path
          required: true
          schema: { type: integer }
      responses:
        "200":
          description: found
          content:
            application/json:
              schema: { $ref: "#/components/schemas/Student" }
        "404":
          description: not found
```

There are two approaches: **code first** (the description is generated from the code, in ASP.NET Core with the package `Microsoft.AspNetCore.OpenApi` via `builder.Services.AddOpenApi()` and `app.MapOpenApi()`, in Rust for example with the crate `utoipa`) and **API first** (the description is designed and agreed first, and server skeletons and client libraries are generated from it).

## Authentication

Because REST is stateless, every request has to show who is making it. Credentials belong in headers, never in the URL, since URLs end up in log files and the browser history. All methods require **HTTPS**.

| Method         | How it works                                                                                 | Use                                   |
| -------------- | -------------------------------------------------------------------------------------------- | ------------------------------------- |
| **API key**    | a secret, random string in a header, for example `X-API-Key: 9f2c...`. Identifies the calling application | server-to-server, public data APIs with a quota |
| **JWT** (_JSON Web Token_, RFC 7519) | After login, the server issues a **signed** token: `header.payload.signature`, each Base64url-encoded. The payload contains **claims** such as user ID, roles and expiry time (`exp`). The client sends it as `Authorization: Bearer <token>`, and the server only checks the signature and needs no session database | SPAs, mobile apps, microservices |
| **OAuth 2.0** (RFC 6749) | framework for **delegated authorisation**: a user allows an application to access an API on their behalf without giving it their password. An **authorisation server** issues an access token for this. **OpenID Connect** adds login ("Sign in with Microsoft") | third-party access, single sign-on |

:::caution[A JWT is not encrypted]
Anyone who has a JWT can read its payload, because Base64url is just an encoding. The signature only prevents modification. Passwords and other secrets therefore do not belong in it, and the expiry time should be short, because a stolen token remains valid until then.
:::

## GraphQL and gRPC

| Feature          | REST                                  | GraphQL                                          | gRPC                                           |
| ---------------- | ------------------------------------- | ------------------------------------------------ | ---------------------------------------------- |
| Origin           | Fielding, 2000                        | Facebook, published 2015                          | Google, published 2015                          |
| Endpoints        | many, one per resource                | **one** (`POST /graphql`)                         | methods of a service, like function calls      |
| Data format      | usually JSON                          | JSON                                              | **Protocol Buffers** (binary, compact)         |
| Interface description | optional (OpenAPI)               | mandatory **schema** with types                   | mandatory `.proto` file, code is generated     |
| Who decides the fields? | the server                     | the **client** queries exactly the fields it needs | the server                                    |
| Transport        | HTTP/1.1, HTTP/2, HTTP/3               | HTTP                                              | **HTTP/2**, streaming in both directions       |
| HTTP caching     | easy (GET URLs)                        | difficult (everything via POST)                   | not intended                                    |
| Use              | public APIs, simple CRUD services      | frontends with many different data requirements   | fast communication between microservices       |

REST has two typical problems: **overfetching** (the endpoint returns more fields than needed) and **underfetching** (several requests are needed for one view, for example students, then their class, then their grades). GraphQL solves both with a single query:

```graphql
query {
  student(id: 17) {
    name
    schoolClass { name teacher { name } }
    grades(subject: "SEW") { value }
  }
}
```

In return, the server is more complex, and expensive, deeply nested queries have to be limited. gRPC is very efficient thanks to the binary format and HTTP/2, but browsers can only reach it via the workaround **gRPC-Web**.

## Implementing a REST API

The following example implements the same API in C# and Rust: students are managed in an in-memory list (in a real application a database would be used here, see [Databases](/en/databases/)).

| Endpoint                     | Effect                           |
| ---------------------------- | -------------------------------- |
| `GET /api/students`          | all students                     |
| `GET /api/students/{id}`     | one student or `404`             |
| `POST /api/students`         | create, `201` with `Location`    |
| `PUT /api/students/{id}`     | replace, `200` or `404`          |
| `DELETE /api/students/{id}`  | delete, `204` or `404`           |

In C# you use **ASP.NET Core** with **minimal APIs**: `WebApplication` creates the server (Kestrel), and `MapGet`, `MapPost` and so on map URL patterns to lambda functions. Parameters are bound automatically from the path, the query and the JSON body. In Rust you use the web framework **axum** on the asynchronous runtime **tokio**, with **serde** for JSON. Handlers are `async` functions whose parameters are **extractors** (`Path`, `State`, `Json`).

Because the server processes several requests at the same time, the shared list is protected with a lock (see [Concurrency](/en/software-development/concurrency/)).

```csharp
using Microsoft.AspNetCore.Builder;
using Microsoft.AspNetCore.Http;

// in a project created with "dotnet new web" these usings are already implicit
var builder = WebApplication.CreateBuilder(args);
var app = builder.Build();

var store = new StudentStore();
var students = app.MapGroup("/api/students");

students.MapGet("/", () => store.GetAll());

students.MapGet("/{id:int}", (int id) =>
    store.Find(id) is Student student ? Results.Ok(student) : Results.NotFound());

students.MapPost("/", (StudentInput input) =>
{
    if (string.IsNullOrWhiteSpace(input.Name))
        return Results.ValidationProblem(new Dictionary<string, string[]>
        {
            ["Name"] = ["The name must not be empty."],
        });
    Student created = store.Add(input);
    return Results.Created($"/api/students/{created.Id}", created);
});

students.MapPut("/{id:int}", (int id, StudentInput input) =>
    store.Replace(id, input) is Student updated ? Results.Ok(updated) : Results.NotFound());

students.MapDelete("/{id:int}", (int id) =>
    store.Remove(id) ? Results.NoContent() : Results.NotFound());

app.Run("http://localhost:5000");

public record Student(int Id, string Name, string SchoolClass);

public record StudentInput(string Name, string SchoolClass);

public class StudentStore
{
    private readonly Lock gate = new();
    private readonly List<Student> students =
        [new(1, "Anna Huber", "3AHIT"), new(2, "Lukas Gruber", "3BHIT")];
    private int nextId = 3;

    public List<Student> GetAll()
    {
        lock (gate) return [.. students];   // a copy so that nobody changes the list from outside
    }

    public Student? Find(int id)
    {
        lock (gate) return students.Find(s => s.Id == id);
    }

    public Student Add(StudentInput input)
    {
        lock (gate)
        {
            var student = new Student(nextId++, input.Name, input.SchoolClass);
            students.Add(student);
            return student;
        }
    }

    public Student? Replace(int id, StudentInput input)
    {
        lock (gate)
        {
            int index = students.FindIndex(s => s.Id == id);
            if (index < 0) return null;
            students[index] = new Student(id, input.Name, input.SchoolClass);
            return students[index];
        }
    }

    public bool Remove(int id)
    {
        lock (gate) return students.RemoveAll(s => s.Id == id) > 0;
    }
}
```

```rust
use axum::{
    Json, Router,
    extract::{Path, State},
    http::{StatusCode, header},
    response::IntoResponse,
    routing::get,
};
use serde::{Deserialize, Serialize};
use std::sync::{Arc, Mutex};

#[derive(Clone, Serialize)]
#[serde(rename_all = "camelCase")]
struct Student {
    id: u32,
    name: String,
    school_class: String,
}

#[derive(Deserialize)]
#[serde(rename_all = "camelCase")]
struct StudentInput {
    name: String,
    school_class: String,
}

struct Store {
    students: Vec<Student>,
    next_id: u32,
}

// shared state for all requests
type AppState = Arc<Mutex<Store>>;

async fn list(State(state): State<AppState>) -> Json<Vec<Student>> {
    // lock() only fails if another thread panicked while holding the lock
    Json(state.lock().unwrap().students.clone())
}

async fn get_one(State(state): State<AppState>, Path(id): Path<u32>) -> Result<Json<Student>, StatusCode> {
    let store = state.lock().unwrap();
    store.students.iter().find(|s| s.id == id).cloned().map(Json).ok_or(StatusCode::NOT_FOUND)
}

async fn create(State(state): State<AppState>, Json(input): Json<StudentInput>) -> impl IntoResponse {
    if input.name.trim().is_empty() {
        return Err((StatusCode::BAD_REQUEST, "The name must not be empty."));
    }
    let mut store = state.lock().unwrap();
    let student = Student { id: store.next_id, name: input.name, school_class: input.school_class };
    store.next_id += 1;
    store.students.push(student.clone());
    let location = format!("/api/students/{}", student.id);
    Ok((StatusCode::CREATED, [(header::LOCATION, location)], Json(student)))
}

async fn replace(
    State(state): State<AppState>,
    Path(id): Path<u32>,
    Json(input): Json<StudentInput>,
) -> Result<Json<Student>, StatusCode> {
    let mut store = state.lock().unwrap();
    let student = store.students.iter_mut().find(|s| s.id == id).ok_or(StatusCode::NOT_FOUND)?;
    student.name = input.name;
    student.school_class = input.school_class;
    Ok(Json(student.clone()))
}

async fn remove(State(state): State<AppState>, Path(id): Path<u32>) -> StatusCode {
    let mut store = state.lock().unwrap();
    let before = store.students.len();
    store.students.retain(|s| s.id != id);
    if store.students.len() < before { StatusCode::NO_CONTENT } else { StatusCode::NOT_FOUND }
}

#[tokio::main]
async fn main() -> std::io::Result<()> {
    let state: AppState = Arc::new(Mutex::new(Store {
        students: vec![
            Student { id: 1, name: "Anna Huber".into(), school_class: "3AHIT".into() },
            Student { id: 2, name: "Lukas Gruber".into(), school_class: "3BHIT".into() },
        ],
        next_id: 3,
    }));

    let app = Router::new()
        .route("/api/students", get(list).post(create))
        .route("/api/students/{id}", get(get_one).put(replace).delete(remove))
        .with_state(state);

    let listener = tokio::net::TcpListener::bind("127.0.0.1:5000").await?;
    println!("Server running at http://localhost:5000");
    axum::serve(listener, app).await
}
```

Both frameworks check the request before the handler runs: if the body is missing, the JSON is invalid or a path parameter does not match the type (`/api/students/abc`), they automatically respond with a 4xx status code. In ASP.NET Core, the route constraint `{id:int}` ensures that `/api/students/abc` does not match this endpoint at all (`404`). axum responds with `422 Unprocessable Entity` for JSON that does not match the type, and with `415` if `Content-Type: application/json` is missing.

The `std::sync::Mutex` may be used in axum as long as the lock is not held across an `.await`. Otherwise you need `tokio::sync::Mutex`.

## Calling the API

With **curl** from the command line:

```bash
curl http://localhost:5000/api/students
curl -i http://localhost:5000/api/students/1
curl -i -X POST http://localhost:5000/api/students \
     -H "Content-Type: application/json" \
     -d '{"name":"Clara Bauer","schoolClass":"3AHIT"}'
curl -X PUT http://localhost:5000/api/students/3 \
     -H "Content-Type: application/json" \
     -d '{"name":"Clara Bauer","schoolClass":"4AHIT"}'
curl -i -X DELETE http://localhost:5000/api/students/3
```

The response to the POST is:

```http
HTTP/1.1 201 Created
Content-Type: application/json; charset=utf-8
Location: /api/students/3

{"id":3,"name":"Clara Bauer","schoolClass":"3AHIT"}
```

From a program, you call the API with an HTTP client. The methods `GetFromJsonAsync` and `PostAsJsonAsync`, or `.json()` in reqwest, serialise and deserialise automatically. In the browser you use [`fetch`](/en/web-technologies/javascript/#asynchronous-programming). If the frontend runs on a different origin from the API, the server must allow [CORS](/en/web-technologies/http/#cors).

```csharp
using System.Net;
using System.Net.Http.Json;

using var http = new HttpClient { BaseAddress = new Uri("http://localhost:5000/") };

// add a new student
var response = await http.PostAsJsonAsync("api/students", new StudentInput("Clara Bauer", "3AHIT"));
Student? created = await response.Content.ReadFromJsonAsync<Student>();
Console.WriteLine($"{(int)response.StatusCode}, new at {response.Headers.Location}");

// read all
List<Student>? all = await http.GetFromJsonAsync<List<Student>>("api/students");
foreach (var s in all ?? []) Console.WriteLine($"{s.Id}: {s.Name} ({s.SchoolClass})");

// delete
var deleted = await http.DeleteAsync($"api/students/{created!.Id}");
Console.WriteLine(deleted.StatusCode == HttpStatusCode.NoContent ? "deleted" : "not found");
```

```rust
use serde::{Deserialize, Serialize};

#[derive(Debug, Deserialize)]
#[serde(rename_all = "camelCase")]
struct Student {
    id: u32,
    name: String,
    school_class: String,
}

#[derive(Serialize)]
#[serde(rename_all = "camelCase")]
struct StudentInput<'a> {
    name: &'a str,
    school_class: &'a str,
}

fn main() -> Result<(), reqwest::Error> {
    let client = reqwest::blocking::Client::new();
    let base = "http://localhost:5000/api/students";

    // add a new student
    let response = client.post(base).json(&StudentInput { name: "Clara Bauer", school_class: "3AHIT" }).send()?;
    println!("{}, new at {:?}", response.status(), response.headers().get("location"));
    let created: Student = response.json()?;

    // read all
    let all: Vec<Student> = client.get(base).send()?.error_for_status()?.json()?;
    for s in &all {
        println!("{}: {} ({})", s.id, s.name, s.school_class);
    }

    // delete
    let deleted = client.delete(format!("{base}/{}", created.id)).send()?;
    println!("{}", if deleted.status() == reqwest::StatusCode::NO_CONTENT { "deleted" } else { "not found" });
    Ok(())
}
```
