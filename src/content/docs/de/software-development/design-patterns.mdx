In der Softwareentwicklung tauchen ähnliche Probleme immer wieder auf: Wie erzeugt man Objekte, ohne sich an konkrete Klassen zu binden? Wie verbindet man zwei Klassen mit unpassenden Schnittstellen? Wie benachrichtigt man viele Objekte über eine Änderung? **Entwurfsmuster** (_Design Patterns_) sind bewährte Lösungsschablonen für solche wiederkehrenden Probleme.

Ein Entwurfsmuster ist kein fertiger Code, den man kopiert, sondern eine Beschreibung von **Problem**, **Kontext** und **Kern einer Lösung**, die man an die eigene Situation anpasst. Außerdem geben Muster Entwicklerinnen und Entwicklern ein **gemeinsames Vokabular**: Sagt jemand „Das lösen wir mit einem Adapter“, wissen alle Beteiligten sofort, wie die Lösung ungefähr aussieht.

## Die „Gang of Four“

Bekannt wurden Entwurfsmuster durch das Buch _Design Patterns: Elements of Reusable Object-Oriented Software_ (1994) von Erich Gamma, Richard Helm, Ralph Johnson und John Vlissides, der sogenannten **„Gang of Four“** (GoF). Darin werden 23 Muster beschrieben und nach ihrem Zweck in drei Kategorien eingeteilt:

| Kategorie            | Zweck                                                                          | Muster                                                                                                   |
| -------------------- | ------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------- |
| **Erzeugungsmuster** | regeln, wie Objekte erstellt werden, und entkoppeln den Code von konkreten Klassen | Singleton, Factory Method, Abstract Factory, Builder, Prototype                                      |
| **Strukturmuster**   | setzen Klassen und Objekte zu größeren Strukturen zusammen                      | Adapter, Bridge, Composite, Decorator, Facade, Flyweight, Proxy                                          |
| **Verhaltensmuster** | regeln die Zusammenarbeit und Aufgabenverteilung zwischen Objekten              | Chain of Responsibility, Command, Interpreter, Iterator, Mediator, Memento, Observer, State, Strategy, Template Method, Visitor |

Die Muster werden im deutschen Sprachraum meist mit ihren englischen Namen bezeichnet. Die deutsche Übersetzung des Buches verwendet zum Teil eigene Namen wie „Fabrikmethode“, „Erbauer“, „Beobachter“ oder „Zustand“.

### Wann sollte man Entwurfsmuster einsetzen?

Entwurfsmuster sind Werkzeuge und kein Selbstzweck. Ein Muster lohnt sich, wenn das Problem, das es löst, tatsächlich auftritt, etwa wenn eine Klasse durch viele `if`-Abfragen unübersichtlich wird oder wenn inkompatible Schnittstellen verbunden werden müssen. Wer Muster „auf Vorrat“ einbaut, macht den Code unnötig komplex ([YAGNI](/de/software-development/clean-code/#grundprinzipien)).

Fast alle Muster beruhen auf zwei Grundsätzen aus dem GoF-Buch:

- **Gegen Schnittstellen programmieren, nicht gegen Implementierungen.**
- **Komposition der Vererbung vorziehen** (siehe [Objektorientierte Programmierung](/de/software-development/object-oriented-programming/#komposition-statt-vererbung)).

:::note[Muster und Sprachmerkmale]
Viele Muster gleichen fehlende Sprachmerkmale der objektorientierten Sprachen der 1990er-Jahre aus. In modernen Sprachen sind einige davon direkt eingebaut: Ein **Iterator** ist in C# `IEnumerable` mit `yield`, in Rust das Trait `Iterator`. Eine **Strategy** ist oft einfach ein Lambda bzw. eine Closure. Den **Observer** bieten C#-Events. Und den **Visitor** ersetzt in Rust häufig ein Enum mit `match`. Die Beispiele zeigen jeweils die klassische Form und, wo es sich anbietet, die idiomatische Kurzform.
:::

## Erzeugungsmuster

### Singleton

**Zweck**: Stellt sicher, dass es von einer Klasse **genau eine Instanz** gibt, und bietet einen globalen Zugriffspunkt darauf.

**Problem**: Manche Objekte darf es nur einmal geben, etwa die Konfiguration einer Anwendung, einen Verbindungspool oder einen Logger. Würden mehrere Instanzen erzeugt, könnten sie unterschiedliche Zustände haben.

**Lösung**: Der Konstruktor wird **privat**, damit niemand von außen Instanzen erzeugen kann. Eine statische Eigenschaft oder Methode gibt immer dieselbe, intern gespeicherte Instanz zurück. In Mehr-Thread-Programmen muss die Erzeugung **threadsicher** sein. In C# erledigt das die Klasse `Lazy<T>`, in Rust `LazyLock` bzw. `OnceLock`, die die Instanz erst beim ersten Zugriff erzeugen (**Lazy Initialization**).

<Tabs syncKey="code">
<TabItem label="C#">

```csharp
AppConfig.Instance.Set("theme", "dark");
Console.WriteLine(AppConfig.Instance.Get("theme"));          // dark
Console.WriteLine(ReferenceEquals(AppConfig.Instance, AppConfig.Instance)); // True

public sealed class AppConfig
{
    // Lazy<T> ist standardmäßig threadsicher
    private static readonly Lazy<AppConfig> LazyInstance = new(() => new AppConfig());

    public static AppConfig Instance => LazyInstance.Value;

    private readonly Dictionary<string, string> _values = [];

    private AppConfig() { } // privater Konstruktor

    public void Set(string key, string value) => _values[key] = value;
    public string? Get(string key) => _values.GetValueOrDefault(key);
}
```

</TabItem>
<TabItem label="Rust">

```rust
use std::collections::HashMap;
use std::sync::{LazyLock, Mutex};

// globale Instanz, beim ersten Zugriff threadsicher erzeugt
static CONFIG: LazyLock<Mutex<HashMap<String, String>>> =
    LazyLock::new(|| Mutex::new(HashMap::new()));

fn main() {
    CONFIG.lock().unwrap().insert("theme".into(), "dark".into());
    println!("{:?}", CONFIG.lock().unwrap().get("theme")); // Some("dark")
}
```

</TabItem>
</Tabs>

**Vorteile und Nachteile**:

- ✅ Es existiert garantiert nur eine Instanz, die erst bei Bedarf erzeugt wird.
- ❌ Ein Singleton ist **globaler Zustand** und erhöht die [Kopplung](/de/software-development/software-metrics/#koppelung), weil viele Klassen direkt darauf zugreifen.
- ❌ Singletons lassen sich in Unit-Tests schwer austauschen. In Anwendungen mit [Dependency Injection](/de/software-development/software-architecture/#dependency-injection) registriert man Klassen daher meist als Singleton-Service, statt das Muster selbst zu implementieren. Rust macht globale veränderbare Daten bewusst umständlich (`Mutex`, `LazyLock`), um Data Races auszuschließen.

### Factory Method

**Zweck**: Definiert eine Methode zum Erzeugen von Objekten, wobei **Unterklassen entscheiden**, welche konkrete Klasse erzeugt wird.

**Problem**: Eine Logistik-Anwendung arbeitete anfangs nur mit Lastwagen. Nun sollen auch Schiffe dazukommen. Steht überall im Code `new Truck()`, muss jede dieser Stellen geändert werden.

**Lösung**: Statt Objekte direkt mit `new` zu erzeugen, ruft der Code eine **Fabrikmethode** auf (`CreateTransport()`). Die Basisklasse (_Creator_) enthält die gemeinsame Logik, und jede Unterklasse überschreibt die Fabrikmethode und liefert ihr eigenes Produkt. Der restliche Code arbeitet nur mit der Schnittstelle des Produkts.

<Tabs syncKey="code">
<TabItem label="C#">

```csharp
Logistics[] companies = [new RoadLogistics(), new SeaLogistics()];
foreach (var company in companies)
{
    company.PlanDelivery("Krems");
}
// Lieferung nach Krems: Lastwagen fährt über die Straße
// Lieferung nach Krems: Schiff fährt über die Donau

public interface ITransport
{
    string Deliver();
}

public class Truck : ITransport
{
    public string Deliver() => "Lastwagen fährt über die Straße";
}

public class Ship : ITransport
{
    public string Deliver() => "Schiff fährt über die Donau";
}

// Creator mit gemeinsamer Logik
public abstract class Logistics
{
    protected abstract ITransport CreateTransport(); // Fabrikmethode

    public void PlanDelivery(string city)
    {
        ITransport transport = CreateTransport();
        Console.WriteLine($"Lieferung nach {city}: {transport.Deliver()}");
    }
}

public class RoadLogistics : Logistics
{
    protected override ITransport CreateTransport() => new Truck();
}

public class SeaLogistics : Logistics
{
    protected override ITransport CreateTransport() => new Ship();
}
```

</TabItem>
<TabItem label="Rust">

```rust
trait Transport {
    fn deliver(&self) -> String;
}

struct Truck;
struct Ship;

impl Transport for Truck {
    fn deliver(&self) -> String { "Lastwagen fährt über die Straße".into() }
}

impl Transport for Ship {
    fn deliver(&self) -> String { "Schiff fährt über die Donau".into() }
}

// Creator: die Fabrikmethode ist erforderlich, plan_delivery eine Standardmethode
trait Logistics {
    fn create_transport(&self) -> Box<dyn Transport>;

    fn plan_delivery(&self, city: &str) {
        let transport = self.create_transport();
        println!("Lieferung nach {city}: {}", transport.deliver());
    }
}

struct RoadLogistics;
struct SeaLogistics;

impl Logistics for RoadLogistics {
    fn create_transport(&self) -> Box<dyn Transport> { Box::new(Truck) }
}

impl Logistics for SeaLogistics {
    fn create_transport(&self) -> Box<dyn Transport> { Box::new(Ship) }
}

fn main() {
    let companies: Vec<Box<dyn Logistics>> = vec![Box::new(RoadLogistics), Box::new(SeaLogistics)];
    for company in &companies {
        company.plan_delivery("Krems");
    }
}
```

</TabItem>
</Tabs>

**Vorteile und Nachteile**:

- ✅ Neue Produkte erfordern nur eine neue Unterklasse ([Open/Closed Principle](/de/software-development/clean-code/#openclosed-principle)).
- ✅ Die Erzeugung ist an einer Stelle gebündelt.
- ❌ Für jedes Produkt entsteht eine zusätzliche Creator-Klasse.

Häufig verwendet man auch eine **einfache Fabrik** (_Simple Factory_): eine statische Methode wie `Transport.Create("ship")`, die je nach Parameter ein Objekt erzeugt. Sie ist kein GoF-Muster, aber in der Praxis sehr verbreitet. Statische Methoden wie `int.Parse` oder `TimeSpan.FromSeconds` heißen auch **Factory-Methoden** im weiteren Sinn.

### Abstract Factory

**Zweck**: Stellt eine Schnittstelle bereit, um **Familien zusammengehöriger Objekte** zu erzeugen, ohne ihre konkreten Klassen zu kennen.

**Problem**: Eine Oberfläche soll ein helles und ein dunkles Design unterstützen. Schaltflächen, Textfelder und Menüs müssen jeweils zusammenpassen: Eine helle Schaltfläche neben einem dunklen Textfeld wäre ein Fehler.

**Lösung**: Für jede Produktfamilie gibt es eine **konkrete Fabrik**, die alle Produkte dieser Familie erzeugt. Der Code verwendet nur die abstrakte Fabrik und die Produkt-Schnittstellen. Welche Familie verwendet wird, entscheidet man an einer einzigen Stelle, etwa beim Programmstart.

```csharp
public class DarkTextBox : ITextBox { public string Render() => "[____] schwarz"; }

    public IButton CreateButton() => new LightButton();
    public ITextBox CreateTextBox() => new LightTextBox();
}
```

**Vorteile und Nachteile**:

- ✅ Produkte einer Familie passen garantiert zusammen.
- ✅ Die Familie lässt sich an einer Stelle austauschen.
- ❌ Ein neues Produkt (etwa eine Checkbox) erfordert Änderungen an der Schnittstelle und an allen Fabriken.

### Builder

**Zweck**: Trennt die **schrittweise Konstruktion** eines komplexen Objekts von seiner Darstellung.

**Problem**: Ein Objekt hat viele optionale Bestandteile, etwa eine HTTP-Anfrage mit Methode, URL, Headern, Body und Timeout. Ein Konstruktor mit zehn Parametern, von denen die meisten `null` sind, ist unlesbar und fehleranfällig (_Telescoping Constructor_).

**Lösung**: Ein **Builder** sammelt die Angaben über einzelne, gut benannte Methoden, die man verketten kann (**Fluent Interface**). Erst `Build()` erzeugt das fertige, meist unveränderliche Objekt und prüft dabei, ob alle Pflichtangaben vorhanden sind. In Rust ist das Builder-Muster sehr verbreitet, weil es keine optionalen Parameter gibt.

<Tabs syncKey="code">
<TabItem label="C#">

```csharp
HttpRequestSpec request = new RequestBuilder("https://api.example.com/orders")
    .Method("POST")
    .Header("Content-Type", "application/json")
    .Body("""{"item": "Tastatur"}""")
    .Timeout(TimeSpan.FromSeconds(5))
    .Build();

Console.WriteLine(request);

public record HttpRequestSpec(string Method, string Url, IReadOnlyDictionary<string, string> Headers,
    string? Body, TimeSpan Timeout)
{
    public override string ToString() =>
        $"{Method} {Url} ({Headers.Count} Header, Timeout {Timeout.TotalSeconds} s)";
}

public class RequestBuilder(string url)
{
    private string _method = "GET";
    private readonly Dictionary<string, string> _headers = [];
    private string? _body;
    private TimeSpan _timeout = TimeSpan.FromSeconds(30);

    public RequestBuilder Method(string method) { _method = method; return this; }
    public RequestBuilder Header(string name, string value) { _headers[name] = value; return this; }
    public RequestBuilder Body(string body) { _body = body; return this; }
    public RequestBuilder Timeout(TimeSpan timeout) { _timeout = timeout; return this; }

    public HttpRequestSpec Build()
    {
        if (_method == "GET" && _body is not null)
            throw new InvalidOperationException("GET-Anfragen haben keinen Body");
        return new HttpRequestSpec(_method, url, _headers, _body, _timeout);
    }
}
```

</TabItem>
<TabItem label="Rust">

```rust
use std::collections::HashMap;
use std::time::Duration;

#[derive(Debug)]
struct HttpRequestSpec {
    method: String,
    url: String,
    headers: HashMap<String, String>,
    body: Option<String>,
    timeout: Duration,
}

struct RequestBuilder {
    method: String,
    url: String,
    headers: HashMap<String, String>,
    body: Option<String>,
    timeout: Duration,
}

impl RequestBuilder {
    fn new(url: &str) -> Self {
        RequestBuilder {
            method: "GET".into(),
            url: url.into(),
            headers: HashMap::new(),
            body: None,
            timeout: Duration::from_secs(30),
        }
    }

    // jede Methode übernimmt self und gibt es zurück: Verkettung ohne Kopien
    fn method(mut self, method: &str) -> Self { self.method = method.into(); self }
    fn header(mut self, name: &str, value: &str) -> Self { self.headers.insert(name.into(), value.into()); self }
    fn body(mut self, body: &str) -> Self { self.body = Some(body.into()); self }
    fn timeout(mut self, timeout: Duration) -> Self { self.timeout = timeout; self }

    fn build(self) -> Result<HttpRequestSpec, String> {
        if self.method == "GET" && self.body.is_some() {
            return Err("GET-Anfragen haben keinen Body".into());
        }
        Ok(HttpRequestSpec {
            method: self.method,
            url: self.url,
            headers: self.headers,
            body: self.body,
            timeout: self.timeout,
        })
    }
}

fn main() {
    let request = RequestBuilder::new("https://api.example.com/orders")
        .method("POST")
        .header("Content-Type", "application/json")
        .body(r#"{"item": "Tastatur"}"#)
        .timeout(Duration::from_secs(5))
        .build()
        .unwrap();
    println!("{} {} ({} Header, Timeout {:?})", request.method, request.url, request.headers.len(), request.timeout);
}
```

</TabItem>
</Tabs>

**Vorteile und Nachteile**:

- ✅ Lesbare Erzeugung von Objekten mit vielen optionalen Teilen.
- ✅ Das fertige Objekt kann unveränderlich sein, Prüfungen erfolgen an einer Stelle.
- ❌ Zusätzliche Klasse mit fast denselben Feldern wie das Produkt.

Beispiele aus den Standardbibliotheken: `StringBuilder`, `WebApplication.CreateBuilder()` in ASP.NET Core, `std::thread::Builder` und `std::process::Command` in Rust. Im GoF-Buch gibt es zusätzlich einen **Director**, der die Bauschritte in einer festen Reihenfolge aufruft, etwa um verschiedene Dokumentformate mit demselben Ablauf zu erzeugen.

### Prototype

**Zweck**: Erzeugt neue Objekte, indem ein bestehendes Objekt (der **Prototyp**) **kopiert** wird.

**Problem**: Die Erzeugung eines Objekts ist aufwendig (etwa weil Daten geladen oder berechnet werden müssen), oder man kennt nur die Schnittstelle eines Objekts, nicht seine konkrete Klasse, und möchte trotzdem eine Kopie anlegen.

**Lösung**: Das Objekt bietet selbst eine Methode zum Klonen an. Wichtig ist der Unterschied zwischen **flacher Kopie** (_shallow copy_: Referenzen werden kopiert, beide Objekte teilen sich die referenzierten Objekte) und **tiefer Kopie** (_deep copy_: auch alle referenzierten Objekte werden kopiert). In Rust ist das Muster als Trait `Clone` eingebaut, das immer eine vollständige, eigenständige Kopie erzeugt.

<Tabs syncKey="code">
<TabItem label="C#">

```csharp
var template = new Document("Vorlage Zeugnis", ["Kopfzeile", "Unterschrift"]);

// with erzeugt bei Records nur eine flache Kopie: die Liste wird geteilt
var shallow = template with { Title = "Flache Kopie" };
shallow.Sections.Add("Neuer Abschnitt");
Console.WriteLine(template.Sections.Count); // 3, die Vorlage wurde mitverändert!

var original = new Document("Vorlage Zeugnis", ["Kopfzeile", "Unterschrift"]);
var deep = original.DeepClone();
deep.Sections.Add("Neuer Abschnitt");
Console.WriteLine(original.Sections.Count); // 2, die Vorlage bleibt unverändert

public record Document(string Title, List<string> Sections)
{
    public Document DeepClone() => this with { Sections = new List<string>(Sections) };
}
```

</TabItem>
<TabItem label="Rust">

```rust
#[derive(Clone, Debug)]
struct Document {
    title: String,
    sections: Vec<String>,
}

fn main() {
    let template = Document {
        title: "Vorlage Zeugnis".into(),
        sections: vec!["Kopfzeile".into(), "Unterschrift".into()],
    };

    // clone kopiert auch den Vec: immer eine tiefe Kopie der eigenen Daten
    let mut copy = template.clone();
    copy.title = "Zeugnis 3AHIT".into();
    copy.sections.push("Neuer Abschnitt".into());

    println!("{}", template.sections.len()); // 2
    println!("{}", copy.sections.len());     // 3
}
```

</TabItem>
</Tabs>

**Vorteile und Nachteile**:

- ✅ Kopien ohne Kenntnis der konkreten Klasse und ohne aufwendige Neuerzeugung.
- ❌ Tiefe Kopien sind bei verschachtelten Objekten und zyklischen Referenzen schwierig. Das Interface `ICloneable` in .NET legt nicht fest, ob flach oder tief kopiert wird, und gilt deshalb als ungünstig.

## Strukturmuster

### Adapter

**Zweck**: Passt die **Schnittstelle einer Klasse** an eine andere Schnittstelle an, die der Client erwartet.

**Problem**: Eine Wetterstation arbeitet mit dem Interface `ITemperatureSensor`, das Grad Celsius liefert. Ein vorhandener Sensor eines anderen Herstellers hat eine ganz andere Schnittstelle und liefert Grad Fahrenheit. Seinen Code kann man nicht ändern.

**Lösung**: Ein **Adapter** implementiert die erwartete Schnittstelle und übersetzt jeden Aufruf in einen Aufruf des vorhandenen Objekts (des **Adaptees**). Er wirkt wie ein Reisestecker-Adapter. Die hier gezeigte Variante heißt **Objektadapter**, weil der Adapter das Objekt enthält. Beim **Klassenadapter** erbt der Adapter vom Adaptee, was Mehrfachvererbung voraussetzt und in C# daher kaum verwendet wird.

<Tabs syncKey="code">
<TabItem label="C#">

```csharp
ITemperatureSensor sensor = new FahrenheitSensorAdapter(new LegacyFahrenheitSensor());
Console.WriteLine($"{sensor.ReadCelsius():F1} °C"); // 21.5 °C

// erwartete Schnittstelle
public interface ITemperatureSensor
{
    double ReadCelsius();
}

// vorhandene Klasse mit unpassender Schnittstelle (Adaptee)
public class LegacyFahrenheitSensor
{
    public double GetTemperatureInFahrenheit() => 70.7;
}

// Adapter
public class FahrenheitSensorAdapter(LegacyFahrenheitSensor legacy) : ITemperatureSensor
{
    public double ReadCelsius() => (legacy.GetTemperatureInFahrenheit() - 32) * 5 / 9;
}
```

</TabItem>
<TabItem label="Rust">

```rust
// erwartete Schnittstelle
trait TemperatureSensor {
    fn read_celsius(&self) -> f64;
}

// vorhandener Typ mit unpassender Schnittstelle (Adaptee)
struct LegacyFahrenheitSensor;

impl LegacyFahrenheitSensor {
    fn get_temperature_in_fahrenheit(&self) -> f64 { 70.7 }
}

// Adapter
struct FahrenheitSensorAdapter {
    legacy: LegacyFahrenheitSensor,
}

impl TemperatureSensor for FahrenheitSensorAdapter {
    fn read_celsius(&self) -> f64 {
        (self.legacy.get_temperature_in_fahrenheit() - 32.0) * 5.0 / 9.0
    }
}

fn main() {
    let sensor: Box<dyn TemperatureSensor> =
        Box::new(FahrenheitSensorAdapter { legacy: LegacyFahrenheitSensor });
    println!("{:.1} °C", sensor.read_celsius()); // 21.5 °C
}
```

</TabItem>
</Tabs>

**Vorteile und Nachteile**:

- ✅ Bestehender Code (auch fremde Bibliotheken) lässt sich ohne Änderung weiterverwenden.
- ✅ Die Umwandlungslogik ist an einer Stelle gekapselt.
- ❌ Zusätzliche Klasse; bei sehr unterschiedlichen Schnittstellen wird der Adapter aufwendig.

Typische Einsatzfälle sind die Einbindung alter Systeme (_Legacy-Code_), fremder APIs und Hardware-Treiber. In .NET ist `StreamReader` ein Adapter, der einen Bytestrom als Textquelle nutzbar macht.

### Bridge

**Zweck**: Trennt eine **Abstraktion von ihrer Implementierung**, sodass beide unabhängig voneinander erweitert werden können.

**Problem**: Es gibt verschiedene Fernbedienungen (einfach, erweitert) und verschiedene Geräte (Fernseher, Radio). Mit Vererbung bräuchte man für jede Kombination eine eigene Klasse: `BasicTvRemote`, `BasicRadioRemote`, `AdvancedTvRemote` usw. Mit jeder neuen Fernbedienung oder jedem neuen Gerät wächst die Zahl der Klassen multiplikativ.

**Lösung**: Man teilt die Hierarchie in zwei: Die **Abstraktion** (Fernbedienung) enthält eine Referenz auf die **Implementierung** (Gerät) und delegiert die eigentliche Arbeit an sie. Beide Seiten können unabhängig erweitert werden. Aus $m \cdot n$ Klassen werden $m + n$.

<Tabs syncKey="code">
<TabItem label="C#">

```csharp
var remote = new AdvancedRemote(new Radio());
remote.TogglePower();
remote.VolumeUp();
remote.Mute();
```

### Composite

**Zweck**: Setzt Objekte zu **Baumstrukturen** zusammen und erlaubt es, einzelne Objekte und Gruppen von Objekten **einheitlich** zu behandeln.

**Problem**: Ein Dateisystem besteht aus Dateien und Ordnern, und Ordner können wieder Dateien und Ordner enthalten. Will man die Gesamtgröße berechnen, müsste man ohne gemeinsame Schnittstelle überall prüfen, ob gerade eine Datei oder ein Ordner vorliegt.

**Lösung**: Blätter (**Leaf**, die Datei) und Container (**Composite**, der Ordner) implementieren dieselbe Schnittstelle (**Component**). Der Container leitet Aufrufe rekursiv an seine Kinder weiter und fasst die Ergebnisse zusammen.

```rust
    File { name: String, size: u64 },
    Folder { name: String, children: Vec<Node> },
}

impl Node {
    fn size(&self) -> u64 {
        match self {
            Node::File { size, .. } => *size,
            Node::Folder { children, .. } => children.iter().map(Node::size).sum(), // rekursiv
        }
    }

        match self {
            Node::File { name, size } => println!("{indent}{name} ({size} KB)"),
            Node::Folder { name, children } => {
                println!("{indent}{name}/");
                for child in children {
                    child.print(&format!("{indent}  "));
                }
            }
        }
```

### Decorator

**Zweck**: Erweitert ein Objekt **dynamisch um zusätzliche Funktionen**, ohne seine Klasse zu ändern oder Unterklassen zu bilden.

**Problem**: Ein Kaffee kann mit Milch, Zucker, Sirup und Sahne bestellt werden, in beliebigen Kombinationen. Für jede Kombination eine Unterklasse (`KaffeeMitMilchUndZucker`) zu erstellen, führt zu einer Explosion an Klassen.

**Lösung**: Ein **Decorator** implementiert dieselbe Schnittstelle wie das Objekt, das er „umhüllt“ (_Wrapper_), und leitet Aufrufe an dieses weiter. Vor oder nach der Weiterleitung fügt er sein eigenes Verhalten hinzu. Da der Decorator selbst wieder die Schnittstelle erfüllt, lassen sich Decorators beliebig ineinander verschachteln.

### Facade

**Zweck**: Bietet eine **vereinfachte Schnittstelle** zu einem komplexen Subsystem.

**Problem**: Um eine Bestellung abzuwickeln, muss der Code den Lagerbestand prüfen, die Zahlung durchführen, die Lieferung beauftragen und eine Bestätigung senden. Jede aufrufende Stelle müsste alle diese Klassen und die richtige Reihenfolge kennen.

**Lösung**: Eine **Fassade** bündelt die Abläufe des Subsystems hinter wenigen, einfachen Methoden. Clients sprechen nur noch mit der Fassade. Das Subsystem selbst bleibt unverändert und kann bei Bedarf weiterhin direkt verwendet werden.

### Flyweight

**Zweck**: Spart Speicher, indem viele ähnliche Objekte die **gemeinsamen Daten teilen**, statt sie jeweils selbst zu speichern.

**Problem**: Ein Spiel zeigt einen Wald mit einer Million Bäumen. Jeder Baum speichert seine Position, aber auch Name, Farbe und Textur seiner Baumart. Die Textur ist mehrere Kilobyte groß und für alle Bäume einer Art gleich. Der Speicher reicht nicht aus.

**Lösung**: Man trennt den Zustand in zwei Teile:

- **Intrinsischer Zustand**: unveränderlich und für viele Objekte gleich (Baumart mit Textur). Er wird im **Flyweight** gespeichert und geteilt.
- **Extrinsischer Zustand**: für jedes Objekt verschieden (Position). Er bleibt im einzelnen Objekt oder wird von außen übergeben.

Eine **Flyweight-Fabrik** liefert für gleiche Schlüssel immer dasselbe geteilte Objekt.

```csharp
        if (!_cache.TryGetValue(name, out var type))
        {
            type = new TreeType(name, color, new byte[64 * 1024]); // große Textur nur einmal
            _cache[name] = type;
        }
        return type;
    }
```

```rust
    name: String,
    color: String,
    texture: Vec<u8>,
```

### Proxy

**Zweck**: Stellt einen **Stellvertreter** für ein anderes Objekt bereit, der den Zugriff darauf kontrolliert.

**Problem**: Eine Wetter-API ist langsam und kostet pro Anfrage Geld. Viele Programmteile fragen dasselbe Wetter mehrmals pro Minute ab. Den Client-Code zu ändern, um überall ein Caching einzubauen, wäre aufwendig.

**Lösung**: Ein **Proxy** implementiert dieselbe Schnittstelle wie das echte Objekt und wird an dessen Stelle verwendet. Er leitet Aufrufe weiter, kann aber vorher oder nachher eigene Arbeit erledigen. Je nach Zweck unterscheidet man:

- **Virtueller Proxy**: erzeugt ein teures Objekt erst, wenn es wirklich gebraucht wird (_Lazy Loading_).
- **Schutz-Proxy** (_Protection Proxy_): prüft Zugriffsrechte, bevor er weiterleitet.
- **Remote-Proxy**: vertritt ein Objekt auf einem anderen Rechner und kümmert sich um die Netzwerkkommunikation.
- **Caching-Proxy**: speichert Ergebnisse zwischen.

```rust
    fn forecast(&self, city: &str) -> String {
        if let Some((value, time)) = self.cache.borrow().get(city) {
            if time.elapsed() < Duration::from_secs(600) {
                return value.clone();
            }
        }
        let value = self.real.forecast(city);
        self.cache.borrow_mut().insert(city.to_string(), (value.clone(), Instant::now()));
        value
    }
}
```

### Chain of Responsibility

**Zweck**: Gibt eine Anfrage entlang einer **Kette von Empfängern** weiter, bis einer sie bearbeitet.

**Problem**: Bestellungen müssen je nach Betrag von verschiedenen Personen freigegeben werden: bis 1 000 € von der Teamleitung, bis 10 000 € von der Abteilungsleitung, darüber von der Geschäftsführung. Eine lange `if`-Kette koppelt den Absender an alle Entscheidungsträger.

**Lösung**: Jeder **Handler** kennt seinen Nachfolger. Er entscheidet, ob er die Anfrage selbst bearbeitet oder an den nächsten weitergibt. Der Absender kennt nur das erste Glied der Kette. Die Kette lässt sich zur Laufzeit zusammenstellen und umbauen.

<Tabs syncKey="code">
<TabItem label="C#">

```csharp
Approver chain = new TeamLead();
chain.SetNext(new DepartmentHead()).SetNext(new ManagingDirector());

foreach (decimal amount in new[] { 450m, 7_200m, 50_000m })
{
    chain.Approve(amount);
}
// 450 €: freigegeben von der Teamleitung
// 7200 €: freigegeben von der Abteilungsleitung
// 50000 €: freigegeben von der Geschäftsführung

public abstract class Approver
{
    private Approver? _next;

    public Approver SetNext(Approver next) => _next = next; // gibt next zurück: Verkettung

    public void Approve(decimal amount)
    {
        if (CanApprove(amount))
            Console.WriteLine($"{amount} €: freigegeben von {Name}");
        else if (_next is not null)
            _next.Approve(amount);
        else
            Console.WriteLine($"{amount} €: niemand darf freigeben");
    }

    protected abstract string Name { get; }
    protected abstract bool CanApprove(decimal amount);
}

public class TeamLead : Approver
{
    protected override string Name => "der Teamleitung";
    protected override bool CanApprove(decimal amount) => amount <= 1_000;
}

public class DepartmentHead : Approver
{
    protected override string Name => "der Abteilungsleitung";
    protected override bool CanApprove(decimal amount) => amount <= 10_000;
}

public class ManagingDirector : Approver
{
    protected override string Name => "der Geschäftsführung";
    protected override bool CanApprove(decimal amount) => true;
}
```

```rust
struct Approver {
    name: &'static str,
    limit: Option<u32>,          // None: unbegrenzt
    next: Option<Box<Approver>>, // Nachfolger in der Kette
}

impl Approver {
    fn approve(&self, amount: u32) {
        if self.limit.is_none_or(|limit| amount <= limit) {
            println!("{amount} €: freigegeben von {}", self.name);
        } else if let Some(next) = &self.next {
            next.approve(amount);
        } else {
            println!("{amount} €: niemand darf freigeben");
        }
    }
}

fn main() {
    let chain = Approver {
        name: "der Teamleitung",
        limit: Some(1_000),
        next: Some(Box::new(Approver {
            name: "der Abteilungsleitung",
            limit: Some(10_000),
            next: Some(Box::new(Approver { name: "der Geschäftsführung", limit: None, next: None })),
        })),
    };
    for amount in [450, 7_200, 50_000] {
```

### Command

**Zweck**: Kapselt eine **Anfrage als Objekt**. Dadurch lassen sich Anfragen als Parameter übergeben, in Warteschlangen stellen, protokollieren und **rückgängig machen**.

**Problem**: Ein Programm soll Aktionen rückgängig machen können (Strg+Z). Ruft eine Schaltfläche einfach eine Methode auf, gibt es danach keine Information mehr darüber, was passiert ist und wie man es umkehrt.

**Lösung**: Jede Aktion wird ein eigenes Objekt mit den Methoden `Execute()` und `Undo()`. Beteiligt sind:

- **Command**: die gemeinsame Schnittstelle.
- **Konkrete Commands**: führen eine bestimmte Aktion aus und wissen, wie man sie rückgängig macht.
- **Receiver**: das Objekt, das die eigentliche Arbeit erledigt (im Beispiel der Roboter).
- **Invoker**: führt Commands aus und merkt sich die ausgeführten Commands auf einem [Stack](/de/software-development/generics-and-collections/#queue-und-stack).

<Tabs syncKey="code">
<TabItem label="C#">

```csharp
var robot = new Robot();
var invoker = new CommandInvoker();
invoker.Execute(new MoveCommand(robot, 1, 0));
invoker.Execute(new MoveCommand(robot, 0, 2));
Console.WriteLine(robot);  // Roboter bei (1, 2)
invoker.Undo();
Console.WriteLine(robot);  // Roboter bei (1, 0)

// Receiver
public class Robot
{
    public int X { get; private set; }
    public int Y { get; private set; }
    public void Move(int dx, int dy) { X += dx; Y += dy; }
    public override string ToString() => $"Roboter bei ({X}, {Y})";
}

public interface ICommand
{
    void Execute();
    void Undo();
}

public class MoveCommand(Robot robot, int dx, int dy) : ICommand
{
    public void Execute() => robot.Move(dx, dy);
    public void Undo() => robot.Move(-dx, -dy);
}

// Invoker mit Verlauf
public class CommandInvoker
{
    private readonly Stack<ICommand> _history = new();

    public void Execute(ICommand command)
    {
        command.Execute();
        _history.Push(command);
    }

    public void Undo()
    {
        if (_history.TryPop(out var command)) command.Undo();
    }
}
```

```rust
// Receiver
#[derive(Debug, Default)]
struct Robot {
    x: i32,
    y: i32,
}

trait Command {
    fn execute(&self, robot: &mut Robot);
    fn undo(&self, robot: &mut Robot);
}

struct MoveCommand {
    dx: i32,
    dy: i32,
}

impl Command for MoveCommand {
    fn execute(&self, robot: &mut Robot) { robot.x += self.dx; robot.y += self.dy; }
    fn undo(&self, robot: &mut Robot) { robot.x -= self.dx; robot.y -= self.dy; }
}

// Invoker mit Verlauf; besitzt den Receiver, damit Rust die Zugriffe prüfen kann
struct CommandInvoker {
    robot: Robot,
    history: Vec<Box<dyn Command>>,
}

impl CommandInvoker {
    fn execute(&mut self, command: Box<dyn Command>) {
        command.execute(&mut self.robot);
        self.history.push(command);
    }

    fn undo(&mut self) {
        if let Some(command) = self.history.pop() {
            command.undo(&mut self.robot);
        }
    }
}

fn main() {
    let mut invoker = CommandInvoker { robot: Robot::default(), history: Vec::new() };
    invoker.execute(Box::new(MoveCommand { dx: 1, dy: 0 }));
    invoker.execute(Box::new(MoveCommand { dx: 0, dy: 2 }));
    println!("{:?}", invoker.robot); // Robot { x: 1, y: 2 }
    invoker.undo();
    println!("{:?}", invoker.robot); // Robot { x: 1, y: 0 }
}
```

**Vorteile und Nachteile**:

- ✅ Rückgängig/Wiederholen, Makros (Liste von Commands), Warteschlangen und Protokolle werden einfach.
- ✅ Der Auslöser (Schaltfläche, Tastenkürzel, Menü) ist vom Empfänger entkoppelt.
- ❌ Für jede Aktion entsteht eine eigene Klasse.

In WPF ist `ICommand` die Grundlage für das Binden von Schaltflächen an das ViewModel (siehe [GUI-Programmierung](/de/software-development/gui-programming/#datenbindung-und-mvvm)).

### Interpreter

**Zweck**: Definiert eine **Grammatik** für eine einfache Sprache und einen Interpreter, der Sätze dieser Sprache auswertet.

**Problem**: Ein Taschenrechner soll Ausdrücke wie `2 * (3 + 4)` auswerten, oder Benutzer sollen in einer Anwendung einfache Regeln formulieren können.

**Lösung**: Jede Regel der Grammatik wird eine eigene Klasse (bzw. Enum-Variante): Zahlen sind **Terminalausdrücke**, Addition und Multiplikation sind **Nichtterminalausdrücke**, die andere Ausdrücke enthalten. Ein Satz der Sprache wird als **Syntaxbaum** dargestellt, und jeder Knoten kann sich selbst auswerten. Der Baum ist ein [Composite](#composite).

<Tabs syncKey="code">
<TabItem label="C#">

```csharp
// Syntaxbaum für 2 * (3 + 4)
IExpression expression = new Multiply(new Number(2), new Add(new Number(3), new Number(4)));
Console.WriteLine($"{expression} = {expression.Evaluate()}"); // (2 * (3 + 4)) = 14

public interface IExpression
{
    int Evaluate();
}

// Terminalausdruck
public record Number(int Value) : IExpression
{
    public int Evaluate() => Value;
    public override string ToString() => Value.ToString();
}

// Nichtterminalausdrücke
public record Add(IExpression Left, IExpression Right) : IExpression
{
    public int Evaluate() => Left.Evaluate() + Right.Evaluate();
    public override string ToString() => $"({Left} + {Right})";
}

public record Multiply(IExpression Left, IExpression Right) : IExpression
{
    public int Evaluate() => Left.Evaluate() * Right.Evaluate();
    public override string ToString() => $"({Left} * {Right})";
}
```

```rust
// jede Regel der Grammatik ist eine Variante
enum Expr {
    Number(i64),
    Add(Box<Expr>, Box<Expr>),
    Multiply(Box<Expr>, Box<Expr>),
}

impl Expr {
    fn evaluate(&self) -> i64 {
        match self {
            Expr::Number(n) => *n,
            Expr::Add(l, r) => l.evaluate() + r.evaluate(),
            Expr::Multiply(l, r) => l.evaluate() * r.evaluate(),
        }
    }
}

    fn fmt(&self, f: &mut fmt::Formatter) -> fmt::Result {
        match self {
            Expr::Number(n) => write!(f, "{n}"),
            Expr::Add(l, r) => write!(f, "({l} + {r})"),
            Expr::Multiply(l, r) => write!(f, "({l} * {r})"),
        }
    }
}

fn main() {
    use Expr::*;
    // Syntaxbaum für 2 * (3 + 4)
    let expression = Multiply(Box::new(Number(2)), Box::new(Add(Box::new(Number(3)), Box::new(Number(4)))));
```

### Iterator

**Zweck**: Ermöglicht den **sequenziellen Zugriff** auf die Elemente einer Sammlung, ohne ihre innere Struktur offenzulegen.

**Problem**: Eine Sammlung kann ein Array, eine verkettete Liste, ein Baum oder ein Datenbankergebnis sein. Der Code, der die Elemente verarbeitet, soll nicht von dieser Struktur abhängen.

**Lösung**: Ein **Iterator**-Objekt merkt sich die aktuelle Position und bietet eine Methode, um zum nächsten Element zu gehen. Jede Sammlung liefert ihren eigenen Iterator. In C# und Rust ist das Muster Teil der Sprache: `foreach` arbeitet mit `IEnumerable<T>` und `IEnumerator<T>`, `for` mit `IntoIterator` und `Iterator`. Ausführliche Beispiele mit `yield return` und einer eigenen `Iterator`-Implementierung zeigt die Seite [Generics und Collections](/de/software-development/generics-and-collections/#iteratoren).

### Mediator

**Zweck**: Definiert ein Objekt, das das **Zusammenspiel vieler Objekte kapselt**. Die Objekte kommunizieren nicht mehr direkt miteinander, sondern nur noch über den Vermittler.

**Problem**: In einem Chat oder einem Formular, dessen Felder voneinander abhängen, kennt jedes Objekt alle anderen. Bei $n$ Objekten entstehen bis zu $n(n-1)$ direkte Verbindungen, und jede Änderung betrifft viele Klassen.

**Lösung**: Alle Objekte kennen nur den **Mediator** und schicken ihm ihre Nachrichten. Der Mediator entscheidet, wer die Nachricht erhält. Das Kommunikationsgeflecht wird zu einem Stern. Ein Fluglotse ist ein anschauliches Beispiel: Flugzeuge sprechen nicht miteinander, sondern nur mit dem Tower.

<Tabs syncKey="code">
<TabItem label="C#">

```csharp
var room = new ChatRoom();
var anna = new Participant("Anna", room);
var ben = new Participant("Ben", room);
var cem = new Participant("Cem", room);

anna.Send("Hallo zusammen!");
// Ben empfängt von Anna: Hallo zusammen!
// Cem empfängt von Anna: Hallo zusammen!

// Mediator
public class ChatRoom
{
    private readonly List<Participant> _participants = [];

    public void Join(Participant p) => _participants.Add(p);

    public void Broadcast(string from, string message)
    {
        foreach (var p in _participants.Where(p => p.Name != from))
        {
            p.Receive(from, message);
        }
    }
}

public class Participant
{
    private readonly ChatRoom _room;
    public string Name { get; }

    public Participant(string name, ChatRoom room)
    {
        Name = name;
        _room = room;
        room.Join(this);
    }

    public void Send(string message) => _room.Broadcast(Name, message); // nur über den Mediator
    public void Receive(string from, string message) => Console.WriteLine($"{Name} empfängt von {from}: {message}");
}
```

```rust
struct Participant {
    name: String,
    inbox: Vec<String>,
}

// Mediator
#[derive(Default)]
struct ChatRoom {
    participants: Vec<Participant>,
}

impl ChatRoom {
    fn join(&mut self, name: &str) -> usize {
        self.participants.push(Participant { name: name.into(), inbox: Vec::new() });
        self.participants.len() - 1
    }

    fn send(&mut self, from: usize, message: &str) {
        let sender = self.participants[from].name.clone();
        for (id, p) in self.participants.iter_mut().enumerate() {
            if id != from {
                p.inbox.push(format!("von {sender}: {message}"));
            }
        }
    }
}

fn main() {
    let mut room = ChatRoom::default();
    let anna = room.join("Anna");
    room.join("Ben");
    room.join("Cem");

    room.send(anna, "Hallo zusammen!");
    for p in &room.participants {
        println!("{}: {:?}", p.name, p.inbox);
    }
}
```

- ✅ Geringe Kopplung zwischen den Teilnehmern; neue Teilnehmer erfordern keine Änderung der anderen.
- ❌ Der Mediator selbst kann sehr groß und komplex werden.

Im Unterschied zum [Observer](#observer), bei dem Empfänger sich selbst anmelden und der Sender niemanden kennt, steuert beim Mediator eine zentrale Stelle die Kommunikation. In .NET ist die Bibliothek **MediatR** verbreitet, die Anfragen an passende Handler vermittelt.

### Memento

**Zweck**: Hält den **inneren Zustand eines Objekts** fest, ohne die Kapselung zu verletzen, sodass das Objekt später in diesen Zustand zurückversetzt werden kann.

**Problem**: Ein Texteditor soll Zwischenstände speichern, zu denen man zurückkehren kann. Würde eine fremde Klasse alle privaten Felder des Editors auslesen, wäre die Kapselung gebrochen.

**Lösung**: Das Objekt selbst (**Originator**) erzeugt einen Schnappschuss, das **Memento**, und kann aus einem Memento seinen Zustand wiederherstellen. Ein **Caretaker** (etwa ein Verlauf) bewahrt die Mementos auf, kann ihren Inhalt aber nicht verändern.

<Tabs syncKey="code">
<TabItem label="C#">

```csharp
var editor = new Editor();
var history = new Stack<EditorMemento>(); // Caretaker

editor.Type("Hallo");
history.Push(editor.Save());
editor.Type(" Welt");
history.Push(editor.Save());
editor.Type("!!!");

Console.WriteLine(editor.Text);           // Hallo Welt!!!
editor.Restore(history.Pop());
Console.WriteLine(editor.Text);           // Hallo Welt
editor.Restore(history.Pop());
Console.WriteLine(editor.Text);           // Hallo

// Memento: unveränderlicher Schnappschuss
public record EditorMemento(string Text, int Cursor);

// Originator
public class Editor
{
    public string Text { get; private set; } = "";
    private int _cursor;

    public void Type(string s) { Text = Text.Insert(_cursor, s); _cursor += s.Length; }

    public EditorMemento Save() => new(Text, _cursor);

    public void Restore(EditorMemento m) { Text = m.Text; _cursor = m.Cursor; }
}
```

### Observer

**Zweck**: Definiert eine **1:n-Abhängigkeit** zwischen Objekten, sodass bei einer Zustandsänderung eines Objekts alle abhängigen Objekte automatisch benachrichtigt werden.

**Problem**: Ein Wetterdienst misst Temperaturen. Eine Anzeige, ein Diagramm und ein Warnsystem sollen bei jeder neuen Messung aktualisiert werden. Würde der Wetterdienst alle Empfänger direkt aufrufen, müsste man ihn bei jedem neuen Empfänger ändern.

**Lösung**: Das beobachtete Objekt (**Subject**, Publisher) verwaltet eine Liste von **Observern** (Subscriber). Observer melden sich an und ab. Ändert sich der Zustand, ruft das Subject bei allen angemeldeten Observern eine Benachrichtigungsmethode auf. Das Subject kennt die Observer nur über ihre Schnittstelle.

<Tabs syncKey="code">
<TabItem label="C#">

```csharp
var station = new WeatherStation();
var display = new Display();
station.Subscribe(display);
station.Subscribe(new HeatWarning());

station.SetTemperature(24);
station.SetTemperature(33);
station.Unsubscribe(display);
station.SetTemperature(35);

public interface ITemperatureObserver
{
    void Update(double celsius);
}

// Subject
public class WeatherStation
{
    private readonly List<ITemperatureObserver> _observers = [];

    public void Subscribe(ITemperatureObserver o) => _observers.Add(o);
    public void Unsubscribe(ITemperatureObserver o) => _observers.Remove(o);

    public void SetTemperature(double celsius)
    {
        foreach (var o in _observers.ToList()) o.Update(celsius); // Kopie: Abmelden während der Schleife ist erlaubt
    }
}

public class Display : ITemperatureObserver
{
    public void Update(double celsius) => Console.WriteLine($"Anzeige: {celsius} °C");
}

public class HeatWarning : ITemperatureObserver
{
    public void Update(double celsius)
    {
        if (celsius >= 30) Console.WriteLine($"Hitzewarnung bei {celsius} °C!");
    }
}
```

```rust
use std::cell::RefCell;
use std::rc::{Rc, Weak};

trait TemperatureObserver {
    fn update(&self, celsius: f64);
}

// Subject: hält nur schwache Referenzen, damit Observer frei werden können
#[derive(Default)]
struct WeatherStation {
    observers: Vec<Weak<dyn TemperatureObserver>>,
}

impl WeatherStation {
    fn subscribe(&mut self, o: &Rc<dyn TemperatureObserver>) {
        self.observers.push(Rc::downgrade(o));
    }

    fn set_temperature(&mut self, celsius: f64) {
        // nicht mehr existierende Observer automatisch entfernen
        self.observers.retain(|w| w.upgrade().is_some());
        for o in self.observers.iter().filter_map(Weak::upgrade) {
            o.update(celsius);
        }
    }
}

struct Display {
    shown: RefCell<Vec<f64>>,
}

impl TemperatureObserver for Display {
    fn update(&self, celsius: f64) {
        self.shown.borrow_mut().push(celsius);
        println!("Anzeige: {celsius} °C");
    }
}

struct HeatWarning;

impl TemperatureObserver for HeatWarning {
    fn update(&self, celsius: f64) {
        if celsius >= 30.0 {
            println!("Hitzewarnung bei {celsius} °C!");
        }
    }
}

fn main() {
    let mut station = WeatherStation::default();
    let display: Rc<dyn TemperatureObserver> = Rc::new(Display { shown: RefCell::new(Vec::new()) });
    let warning: Rc<dyn TemperatureObserver> = Rc::new(HeatWarning);
    station.subscribe(&display);
    station.subscribe(&warning);

    station.set_temperature(24.0);
    station.set_temperature(33.0);
    drop(display); // Anzeige wird entfernt: automatisch abgemeldet
    station.set_temperature(35.0);
}
```

- ✅ Lose Kopplung: Das Subject kennt keine konkreten Empfänger, neue Observer erfordern keine Änderung am Subject.
- ❌ Die Reihenfolge der Benachrichtigung ist nicht festgelegt; vergessene Abmeldungen führen zu Speicherlecks (_Lapsed Listener Problem_).

In C# sind **Events** die eingebaute Form des Observers (siehe [GUI-Programmierung](/de/software-development/gui-programming/#events-in-c)), außerdem gibt es die Interfaces `IObservable<T>` und `IObserver<T>`, auf denen die Bibliothek Reactive Extensions (Rx) aufbaut. Das Muster ist auch die Grundlage der Datenbindung in MVVM und von **Publish-Subscribe**-Systemen, bei denen ein Nachrichtenbroker zwischen Sendern und Empfängern vermittelt.

### State

**Zweck**: Ermöglicht einem Objekt, sein **Verhalten zu ändern, wenn sich sein innerer Zustand ändert**. Es sieht so aus, als hätte das Objekt seine Klasse gewechselt.

**Problem**: Eine Bestellung kann neu, bezahlt, versandt oder storniert sein. Jede Methode (`Pay`, `Ship`, `Cancel`) enthält ein großes `switch` über den aktuellen Zustand. Mit jedem neuen Zustand müssen alle diese Verzweigungen erweitert werden.

**Lösung**: Jeder Zustand wird eine eigene Klasse mit derselben Schnittstelle. Das Objekt (**Context**) hält eine Referenz auf das aktuelle Zustandsobjekt und delegiert alle zustandsabhängigen Aufrufe dorthin. Ein Zustand entscheidet selbst, in welchen Folgezustand gewechselt wird. Das Muster setzt ein [Zustandsdiagramm](/de/software-development/uml/#zustandsdiagramm) direkt in Code um.

<Tabs syncKey="code">
<TabItem label="C#">

```csharp
var order = new Order();
order.Ship();    // Neue Bestellungen müssen zuerst bezahlt werden.
order.Pay();     // Bezahlt.
order.Ship();    // Versandt.
order.Cancel();  // Versandte Bestellungen können nicht storniert werden.
Console.WriteLine(order.State.Name); // Versandt

public interface IOrderState
{
    string Name { get; }
    IOrderState Pay();
    IOrderState Ship();
    IOrderState Cancel();
}

public class NewState : IOrderState
{
    public string Name => "Neu";
    public IOrderState Pay() { Console.WriteLine("Bezahlt."); return new PaidState(); }
    public IOrderState Ship() { Console.WriteLine("Neue Bestellungen müssen zuerst bezahlt werden."); return this; }
    public IOrderState Cancel() { Console.WriteLine("Storniert."); return new CancelledState(); }
}

public class PaidState : IOrderState
{
    public string Name => "Bezahlt";
    public IOrderState Pay() { Console.WriteLine("Bereits bezahlt."); return this; }
    public IOrderState Ship() { Console.WriteLine("Versandt."); return new ShippedState(); }
    public IOrderState Cancel() { Console.WriteLine("Storniert, Betrag wird erstattet."); return new CancelledState(); }
}

public class ShippedState : IOrderState
{
    public string Name => "Versandt";
    public IOrderState Pay() => this;
    public IOrderState Ship() => this;
    public IOrderState Cancel() { Console.WriteLine("Versandte Bestellungen können nicht storniert werden."); return this; }
}

public class CancelledState : IOrderState
{
    public string Name => "Storniert";
    public IOrderState Pay() => this;
    public IOrderState Ship() => this;
    public IOrderState Cancel() => this;
}

// Context
public class Order
{
    public IOrderState State { get; private set; } = new NewState();
    public void Pay() => State = State.Pay();
    public void Ship() => State = State.Ship();
    public void Cancel() => State = State.Cancel();
}
```

```rust
// In Rust bildet man Zustände idiomatisch als Enum ab;
// match erzwingt, dass jede Kombination behandelt wird.
#[derive(Debug, Clone, Copy, PartialEq)]
enum OrderState {
    New,
    Paid,
    Shipped,
    Cancelled,
}

#[derive(Debug, Clone, Copy)]
enum Event {
    Pay,
    Ship,
    Cancel,
}

impl OrderState {
    fn handle(self, event: Event) -> Result<OrderState, &'static str> {
        use Event::*;
        use OrderState::*;
        match (self, event) {
            (New, Pay) => Ok(Paid),
            (New, Cancel) => Ok(Cancelled),
            (Paid, Ship) => Ok(Shipped),
            (Paid, Cancel) => Ok(Cancelled), // mit Erstattung
            (New, Ship) => Err("Neue Bestellungen müssen zuerst bezahlt werden."),
            (Shipped, Cancel) => Err("Versandte Bestellungen können nicht storniert werden."),
            _ => Err("In diesem Zustand nicht möglich."),
        }
    }
}

fn main() {
    let mut state = OrderState::New;
    for event in [Event::Ship, Event::Pay, Event::Ship, Event::Cancel] {
        match state.handle(event) {
            Ok(next) => {
                println!("{event:?}: {state:?} -> {next:?}");
                state = next;
            }
            Err(message) => println!("{event:?}: {message}"),
        }
    }
    println!("{state:?}"); // Shipped
}
```

</TabItem>
</Tabs>

**Vorteile und Nachteile**:

- ✅ Zustandsabhängiges Verhalten ist pro Zustand gebündelt, große `switch`-Blöcke entfallen.
- ✅ Neue Zustände erfordern keine Änderung bestehender Zustandsklassen.
- ❌ Bei wenigen Zuständen und Übergängen ist ein einfaches Enum übersichtlicher.

Rust bietet zusätzlich das **Typestate-Muster**: Jeder Zustand ist ein eigener Typ (`Order<New>`, `Order<Paid>`), und Methoden wie `ship()` existieren nur für den passenden Typ. Ungültige Übergänge sind dann schon Compilerfehler.

### Strategy

**Zweck**: Definiert eine **Familie austauschbarer Algorithmen**, kapselt jeden einzelnen und macht sie zur Laufzeit austauschbar.

**Problem**: Ein Webshop berechnet Versandkosten: pauschal, nach Gewicht oder ab einem Mindestbestellwert gratis. Stehen alle Varianten in einer Methode mit vielen `if`-Abfragen, muss diese bei jeder neuen Variante geändert werden.

**Lösung**: Jeder Algorithmus kommt in eine eigene Klasse, die eine gemeinsame Schnittstelle (**Strategy**) implementiert. Das verwendende Objekt (**Context**) erhält eine Strategie und ruft sie auf, ohne die konkrete Klasse zu kennen. Die Strategie kann jederzeit ausgetauscht werden.

<Tabs syncKey="code">
<TabItem label="C#">

```csharp
var cart = new ShoppingCart(new WeightBasedShipping());
cart.Add(30m, 2.5);
Console.WriteLine(cart.Total());                  // 43.75

cart.ShippingStrategy = new FreeAboveShipping(25m); // zur Laufzeit wechseln
Console.WriteLine(cart.Total());                  // 30

// als Lambda: eine Strategie mit nur einer Methode ist einfach eine Funktion
Func<decimal, double, decimal> flat = (_, _) => 4.90m;
Console.WriteLine(flat(30m, 2.5));                 // 4.90

public interface IShippingStrategy
{
    decimal Cost(decimal orderValue, double weightKg);
}

public class WeightBasedShipping : IShippingStrategy
{
    public decimal Cost(decimal orderValue, double weightKg) => 3.75m + 4m * (decimal)weightKg;
}

public class FreeAboveShipping(decimal threshold) : IShippingStrategy
{
    public decimal Cost(decimal orderValue, double weightKg) => orderValue >= threshold ? 0 : 4.90m;
}

// Context
public class ShoppingCart(IShippingStrategy strategy)
{
    private decimal _value;
    private double _weight;

    public IShippingStrategy ShippingStrategy { get; set; } = strategy;

    public void Add(decimal price, double weightKg) { _value += price; _weight += weightKg; }

    public decimal Total() => _value + ShippingStrategy.Cost(_value, _weight);
}
```

</TabItem>

```rust
trait ShippingStrategy {
    fn cost(&self, order_cents: u32, weight_kg: f64) -> u32;
}

struct WeightBased;
struct FreeAbove(u32);

impl ShippingStrategy for WeightBased {
    fn cost(&self, _order: u32, weight_kg: f64) -> u32 {
        375 + (400.0 * weight_kg).round() as u32
    }
}

impl ShippingStrategy for FreeAbove {
    fn cost(&self, order: u32, _weight: f64) -> u32 {
        if order >= self.0 { 0 } else { 490 }
    }
}

// Context
struct ShoppingCart {
    value: u32,
    weight: f64,
    strategy: Box<dyn ShippingStrategy>,
}

impl ShoppingCart {
    fn total(&self) -> u32 {
        self.value + self.strategy.cost(self.value, self.weight)
    }
}

fn main() {
    let mut cart = ShoppingCart { value: 3000, weight: 2.5, strategy: Box::new(WeightBased) };
    println!("{}", cart.total());                  // 4375 (Cent)

    cart.strategy = Box::new(FreeAbove(2500));     // zur Laufzeit wechseln
    println!("{}", cart.total());                  // 3000

    // als Closure: eine Strategie mit nur einer Methode ist einfach eine Funktion
    let flat = |_order: u32, _weight: f64| 490;
    println!("{}", flat(3000, 2.5));               // 490
}
```

**Vorteile und Nachteile**:

- ✅ Algorithmen sind austauschbar und einzeln testbar; neue Strategien erfordern keine Änderung des Contexts.
- ✅ Ersetzt Vererbung durch Komposition.
- ❌ Der Client muss die Unterschiede der Strategien kennen, um die richtige zu wählen.

Beispiele aus der Praxis sind die Vergleichsfunktion beim Sortieren (`IComparer<T>`, `sort_by`), Kompressionsverfahren, Routenberechnung (kürzeste oder schnellste Route) und Zahlungsarten.

### Template Method

**Zweck**: Definiert das **Gerüst eines Algorithmus** in einer Methode der Basisklasse und überlässt einzelne Schritte den Unterklassen.

**Problem**: Ein Programm exportiert Berichte als CSV und als HTML. Der Ablauf ist immer gleich: Kopf schreiben, alle Zeilen schreiben, Fuß schreiben. Nur die einzelnen Schritte unterscheiden sich. Den gesamten Ablauf in jede Exportklasse zu kopieren, verletzt [DRY](/de/software-development/clean-code/#grundprinzipien).

**Lösung**: Die Basisklasse enthält die **Schablonenmethode**, die den festen Ablauf vorgibt und dabei abstrakte oder überschreibbare Methoden aufruft. Unterklassen implementieren nur diese Schritte. Optionale Schritte mit leerer Standardimplementierung heißen **Hooks**.

<Tabs syncKey="code">
<TabItem label="C#">

```csharp
string[][] rows = [["Anna", "87"], ["Ben", "54"]];
Console.WriteLine(new CsvExporter().Export(rows));
Console.WriteLine(new HtmlExporter().Export(rows));

public abstract class ReportExporter
{
    // Schablonenmethode: der Ablauf ist festgelegt
    public string Export(string[][] rows)
    {
        var sb = new System.Text.StringBuilder();
        sb.Append(Header());
        foreach (var row in rows) sb.Append(Row(row));
        sb.Append(Footer());
        return sb.ToString();
    }

    protected abstract string Header();
    protected abstract string Row(string[] cells);
    protected virtual string Footer() => ""; // Hook: optional überschreibbar
}

public class CsvExporter : ReportExporter
{
    protected override string Header() => "Name;Punkte\n";
    protected override string Row(string[] cells) => string.Join(";", cells) + "\n";
}

public class HtmlExporter : ReportExporter
{
    protected override string Header() => "<table>\n";
    protected override string Row(string[] cells) => $"<tr><td>{string.Join("</td><td>", cells)}</td></tr>\n";
    protected override string Footer() => "</table>";
}
```

```rust
trait ReportExporter {
    fn header(&self) -> String;
    fn row(&self, cells: &[&str]) -> String;
    fn footer(&self) -> String {
        String::new() // Hook: optional überschreibbar
    }

    // Schablonenmethode als Standardmethode des Traits
    fn export(&self, rows: &[Vec<&str>]) -> String {
        let mut out = self.header();
        for row in rows {
            out += &self.row(row);
        }
        out + &self.footer()
    }
}

struct CsvExporter;
struct HtmlExporter;

impl ReportExporter for CsvExporter {
    fn header(&self) -> String { "Name;Punkte\n".into() }
    fn row(&self, cells: &[&str]) -> String { cells.join(";") + "\n" }
}

impl ReportExporter for HtmlExporter {
    fn header(&self) -> String { "<table>\n".into() }
    fn row(&self, cells: &[&str]) -> String { format!("<tr><td>{}</td></tr>\n", cells.join("</td><td>")) }
    fn footer(&self) -> String { "</table>".into() }
}

fn main() {
    let rows = vec![vec!["Anna", "87"], vec!["Ben", "54"]];
    println!("{}", CsvExporter.export(&rows));
    println!("{}", HtmlExporter.export(&rows));
}
```

</TabItem>
</Tabs>

**Vorteile und Nachteile**:

- ✅ Der gemeinsame Ablauf steht nur an einer Stelle; Unterklassen ändern nur, was sich unterscheidet.
- ❌ Beruht auf Vererbung und koppelt Unterklassen eng an die Basisklasse. Oft ist eine [Strategy](#strategy) für die variablen Schritte die flexiblere Wahl.

Das Prinzip „die Basisklasse ruft die Unterklasse auf“ heißt **Hollywood-Prinzip**: _„Don't call us, we'll call you.“_ Frameworks sind voll davon, etwa die Methoden `OnInitialized` in Blazor oder `Dispose(bool)` in .NET.

### Visitor

**Zweck**: Trennt einen **Algorithmus von der Objektstruktur**, auf der er arbeitet. Neue Operationen lassen sich hinzufügen, ohne die Klassen der Elemente zu ändern.

**Problem**: Ein Grafikprogramm hat die Formen Kreis und Rechteck. Es sollen immer neue Operationen dazukommen: Fläche berechnen, als JSON exportieren, auf dem Bildschirm zeichnen. Jede neue Operation als Methode in alle Formklassen einzubauen, bläht sie auf und mischt unterschiedliche Aufgaben.

**Lösung**: Jede Operation wird ein **Visitor** mit je einer Methode pro Elementtyp (`VisitCircle`, `VisitRectangle`). Jedes Element bietet eine Methode `Accept(visitor)`, die die passende Visit-Methode aufruft. Dieser zweistufige Aufruf heißt **Double Dispatch**: Welche Methode ausgeführt wird, hängt vom Typ des Elements und vom Typ des Visitors ab.

<Tabs syncKey="code">
<TabItem label="C#">

```csharp
IShapeElement[] shapes = [new CircleShape(1), new RectangleShape(2, 3)];
var area = new AreaVisitor();
var json = new JsonVisitor();
foreach (var shape in shapes)
{
    shape.Accept(area);
    Console.WriteLine(shape.Accept(json));
}
Console.WriteLine($"Gesamtfläche: {area.Total:F2}"); // Gesamtfläche: 9.14

public interface IShapeVisitor<T>
{
    T VisitCircle(CircleShape c);
    T VisitRectangle(RectangleShape r);
}

public interface IShapeElement
{
    T Accept<T>(IShapeVisitor<T> visitor);
}

public record CircleShape(double Radius) : IShapeElement
{
    public T Accept<T>(IShapeVisitor<T> visitor) => visitor.VisitCircle(this);
}

public record RectangleShape(double Width, double Height) : IShapeElement
{
    public T Accept<T>(IShapeVisitor<T> visitor) => visitor.VisitRectangle(this);
}

// neue Operationen, ohne die Formen zu ändern
public class AreaVisitor : IShapeVisitor<double>
{
    public double Total { get; private set; }
    public double VisitCircle(CircleShape c) => Total += Math.PI * c.Radius * c.Radius;
    public double VisitRectangle(RectangleShape r) => Total += r.Width * r.Height;
}

public class JsonVisitor : IShapeVisitor<string>
{
    public string VisitCircle(CircleShape c) => $$"""{"type":"circle","r":{{c.Radius}}}""";
    public string VisitRectangle(RectangleShape r) => $$"""{"type":"rect","w":{{r.Width}},"h":{{r.Height}}}""";
}
```

```rust
// klassischer Visitor mit Double Dispatch
trait ShapeVisitor {
    fn visit_circle(&mut self, c: &Circle);
    fn visit_rectangle(&mut self, r: &Rectangle);
}

trait Element {
    fn accept(&self, visitor: &mut dyn ShapeVisitor);
}

struct Circle { radius: f64 }
struct Rectangle { width: f64, height: f64 }

impl Element for Circle {
    fn accept(&self, visitor: &mut dyn ShapeVisitor) { visitor.visit_circle(self); }
}

impl Element for Rectangle {
    fn accept(&self, visitor: &mut dyn ShapeVisitor) { visitor.visit_rectangle(self); }
}

#[derive(Default)]
struct AreaVisitor { total: f64 }

impl ShapeVisitor for AreaVisitor {
    fn visit_circle(&mut self, c: &Circle) { self.total += std::f64::consts::PI * c.radius * c.radius; }
    fn visit_rectangle(&mut self, r: &Rectangle) { self.total += r.width * r.height; }
}

#[derive(Default)]
struct JsonVisitor { out: Vec<String> }

impl ShapeVisitor for JsonVisitor {
    fn visit_circle(&mut self, c: &Circle) {
        self.out.push(format!(r#"{{"type":"circle","r":{}}}"#, c.radius));
    }
    fn visit_rectangle(&mut self, r: &Rectangle) {
        self.out.push(format!(r#"{{"type":"rect","w":{},"h":{}}}"#, r.width, r.height));
    }
}

fn main() {
    let shapes: Vec<Box<dyn Element>> = vec![
        Box::new(Circle { radius: 1.0 }),
        Box::new(Rectangle { width: 2.0, height: 3.0 }),
    ];
    let mut area = AreaVisitor::default();
    let mut json = JsonVisitor::default();
    for shape in &shapes {
        shape.accept(&mut area);
        shape.accept(&mut json);
    }
    println!("{}", json.out.join("\n"));
    println!("Gesamtfläche: {:.2}", area.total); // Gesamtfläche: 9.14
}
```

</TabItem>
</Tabs>

**Vorteile und Nachteile**:

- ✅ Neue Operationen lassen sich leicht hinzufügen, zusammengehörige Logik steckt in einem Visitor.
- ❌ Neue **Elementtypen** sind teuer: Jeder Visitor muss erweitert werden.
- ❌ Visitors brauchen oft Zugriff auf Interna der Elemente.

Ist die Menge der Elementtypen fest, löst man das Problem in Rust einfacher mit einem **Enum und `match`**, und auch C# kann mit Mustervergleich (`shape switch { CircleShape c => ..., ... }`) über Typen verzweigen. Visitors werden in Compilern häufig verwendet, um Syntaxbäume zu durchlaufen, etwa in Roslyn (`CSharpSyntaxWalker`).
