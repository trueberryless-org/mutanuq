Das **relationale Modell** wurde 1970 von Edgar F. Codd bei IBM vorgestellt. Es speichert alle Daten in Tabellen und verknüpft sie nur über Werte, nicht über Zeiger. Ältere hierarchische Datenbanken und Netzwerkdatenbanken verlangten, dass Programme die physischen Zugriffspfade kennen. Im relationalen Modell beschreibt eine Abfrage dagegen nur, **welche** Daten gewünscht sind, und das Datenbanksystem entscheidet selbst, **wie** es sie findet. Diese Trennung ist der Grund, warum relationale Datenbanken seit über 50 Jahren der Standard für strukturierte Daten sind.

## Begriffe

| Formaler Begriff | Umgangssprachlich         | Bedeutung                                                    |
| ---------------- | ------------------------- | ------------------------------------------------------------ |
| **Relation**     | Tabelle                   | Menge von Tupeln mit denselben Attributen                    |
| **Tupel**        | Zeile, Datensatz          | ein einzelner Eintrag, zum Beispiel ein Schüler              |
| **Attribut**     | Spalte, Feld              | eine Eigenschaft mit Namen und Datentyp                      |
| **Domäne**       | Wertebereich, Datentyp    | die erlaubten Werte eines Attributs, etwa ganze Zahlen von 1 bis 5 |
| **Grad**         | Anzahl der Spalten        | Zahl der Attribute einer Relation                            |
| **Kardinalität** | Anzahl der Zeilen         | Zahl der Tupel einer Relation                                |
| **Relationenschema** | Tabellenstruktur      | Name und Attribute, zum Beispiel `Schueler(Id, Vorname, Nachname, KlasseId)` |

Eine **Entität** ist ein eindeutig identifizierbares Objekt der realen Welt, über das Daten gespeichert werden. Gleichartige Entitäten bilden einen **Entitätstyp**, der als Tabelle abgebildet wird. Wie man vom Entwurf zu Tabellen kommt, zeigt die Seite [Datenmodellierung](/de/databases/data-modelling/).

### Eigenschaften einer Relation

Weil eine Relation mathematisch eine **Menge** ist, gelten folgende Regeln:

- Es gibt **keine zwei gleichen Tupel**. Jede Zeile muss sich durch einen Schlüssel unterscheiden.
- Die **Reihenfolge der Zeilen** hat keine Bedeutung. Eine bestimmte Sortierung erhältst du nur mit `ORDER BY`.
- Die **Reihenfolge der Spalten** hat keine Bedeutung. Spalten werden über ihren Namen angesprochen.
- Jeder Wert ist **atomar**, also nicht weiter zerlegbar (siehe [1. Normalform](/de/databases/normalisation/#1-normalform-1nf)).

SQL-Tabellen weichen davon in einem Punkt ab: Ohne Primärschlüssel erlauben sie doppelte Zeilen. Sie sind also streng genommen **Multimengen**.

## Schlüssel

Schlüssel identifizieren Datensätze und verknüpfen Tabellen miteinander.

- **Superschlüssel:** jede Menge von Attributen, die einen Datensatz eindeutig identifiziert.
- **Schlüsselkandidat:** ein minimaler Superschlüssel. Man kann kein Attribut weglassen, ohne die Eindeutigkeit zu verlieren. Eine Tabelle kann mehrere Schlüsselkandidaten haben, etwa `Id` und `Sozialversicherungsnummer`.
- **Primärschlüssel** (`PRIMARY KEY`): der ausgewählte Schlüsselkandidat. Er darf nicht `NULL` sein und sollte sich nie ändern.
- **Alternativschlüssel:** die übrigen Schlüsselkandidaten. Sie werden mit `UNIQUE` abgesichert.
- **Künstlicher Schlüssel** (Surrogatschlüssel): ein eigens eingeführter Schlüssel ohne fachliche Bedeutung, zum Beispiel eine fortlaufende Nummer oder eine GUID. Im Gegensatz dazu hat ein **natürlicher Schlüssel** eine fachliche Bedeutung, etwa die ISBN eines Buches.
- **Zusammengesetzter Schlüssel:** ein Primärschlüssel aus mehreren Spalten, typisch für Zwischentabellen.
- **Fremdschlüssel** (`FOREIGN KEY`): eine Spalte, die auf den Primärschlüssel (oder einen Alternativschlüssel) einer anderen Tabelle verweist.

```sql
CREATE TABLE Klasse (
    Id   INT PRIMARY KEY,
    Name VARCHAR(10) NOT NULL UNIQUE
);

CREATE TABLE Schueler (
    Id       INT PRIMARY KEY,
    Vorname  VARCHAR(50) NOT NULL,
    Nachname VARCHAR(50) NOT NULL,
    KlasseId INT REFERENCES Klasse(Id)
);
```

## Integritätsbedingungen

Integritätsbedingungen sind Regeln, die das Datenbanksystem bei jeder Änderung prüft. Eine Änderung, die eine Regel verletzt, wird abgewiesen. Dadurch kann kein Programm, auch kein fehlerhaftes, ungültige Daten speichern.

| Integrität                   | Regel                                                                                  | Umsetzung in SQL                   |
| ---------------------------- | -------------------------------------------------------------------------------------- | ---------------------------------- |
| **Entitätsintegrität**       | Jede Zeile hat einen eindeutigen Primärschlüssel, der nicht `NULL` ist.                | `PRIMARY KEY`                      |
| **Referentielle Integrität** | Jeder Fremdschlüsselwert verweist auf eine existierende Zeile oder ist `NULL`.         | `FOREIGN KEY ... REFERENCES`       |
| **Domänenintegrität**        | Jeder Wert liegt im erlaubten Wertebereich.                                            | Datentyp, `NOT NULL`, `CHECK`      |
| **Benutzerdefinierte Integrität** | fachliche Regeln, die sich nicht als einfacher Constraint ausdrücken lassen       | [Trigger](/de/databases/sql-advanced/#trigger), Prozeduren |

Was beim Löschen oder Ändern eines referenzierten Datensatzes passiert, legt die **referentielle Aktion** fest:

| Aktion          | Wirkung auf abhängige Zeilen                                        |
| --------------- | ------------------------------------------------------------------- |
| `NO ACTION` / `RESTRICT` | Die Änderung wird abgewiesen (Standard).                   |
| `CASCADE`       | Abhängige Zeilen werden mitgelöscht bzw. mitgeändert.               |
| `SET NULL`      | Der Fremdschlüssel wird auf `NULL` gesetzt.                         |
| `SET DEFAULT`   | Der Fremdschlüssel wird auf seinen Standardwert gesetzt.            |

```sql
CREATE TABLE Fehlstunde (
    Id         INT PRIMARY KEY,
    SchuelerId INT NOT NULL REFERENCES Schueler(Id) ON DELETE CASCADE,
    Datum      DATE NOT NULL,
    Stunden    INT NOT NULL CHECK (Stunden > 0)
);
```

Wird hier ein Schüler gelöscht, löscht die Datenbank auch alle seine Fehlstunden. Die Seite [Datenbankschema](/de/databases/schema/) beschreibt alle Constraints im Detail.

### NULL

`NULL` bedeutet „kein Wert bekannt“ und ist weder 0 noch eine leere Zeichenkette. Jeder Vergleich mit `NULL` ergibt weder wahr noch falsch, sondern **unbekannt**. Deshalb liefert `WHERE KlasseId = NULL` nie eine Zeile, richtig ist `WHERE KlasseId IS NULL`. Die Auswirkungen dieser **dreiwertigen Logik** beschreibt die Seite [SQL-Abfragen](/de/databases/sql-queries/#null-und-dreiwertige-logik).

## Aufbau eines Datenbanksystems

Ein **Datenbanksystem** (DBS) besteht aus der **Datenbank** (den gespeicherten Daten) und dem **Datenbankmanagementsystem** (DBMS, der Software, die sie verwaltet). Ein DBMS übernimmt Aufgaben, die sonst jedes Programm selbst lösen müsste:

| Komponente                      | Aufgabe                                                                                      |
| ------------------------------- | -------------------------------------------------------------------------------------------- |
| **Abfrageprozessor**            | prüft SQL-Anweisungen auf Syntax und Berechtigungen und übersetzt sie in einen Ausführungsplan |
| **Abfrageoptimierer**           | wählt unter vielen gleichwertigen Plänen den günstigsten, etwa ob ein [Index](/de/databases/sql-advanced/#indizes) verwendet wird |
| **Transaktionsverwaltung**      | sorgt für [ACID](/de/databases/transactions/#acid), steuert gleichzeitige Zugriffe über Sperren oder Versionen |
| **Pufferverwaltung**            | hält häufig benötigte Seiten im Arbeitsspeicher                                              |
| **Speicherverwaltung**          | legt Tabellen und Indizes in Dateien auf dem Datenträger ab                                  |
| **Recovery-Komponente**         | stellt nach einem Absturz mit dem Transaktionsprotokoll einen konsistenten Zustand her       |
| **Katalog** (Data Dictionary)   | speichert die Metadaten: welche Tabellen, Spalten, Indizes und Benutzer es gibt              |

Die Metadaten lassen sich selbst mit SQL abfragen, zum Beispiel über die standardisierten Sichten in `information_schema`:

```sql
SELECT table_name, column_name, data_type
FROM information_schema.columns
WHERE table_name = 'schueler'
ORDER BY ordinal_position;
```

PostgreSQL wandelt nicht in Anführungszeichen gesetzte Namen in Kleinbuchstaben um, deshalb steht hier `'schueler'`.

### Codds Regeln

Codd veröffentlichte 1985 zwölf Regeln (nummeriert von 0 bis 12, also eigentlich dreizehn), die ein System erfüllen muss, um als relational zu gelten. Die wichtigsten Gedanken daraus:

- Alle Informationen, auch die Metadaten, werden als Werte in Tabellen dargestellt.
- Jeder Wert ist über Tabellenname, Spaltenname und Primärschlüssel erreichbar.
- `NULL` wird systematisch und unabhängig vom Datentyp behandelt.
- Eine umfassende Sprache deckt Definition, Abfrage, Änderung, Rechte und Transaktionen ab.
- Physische und logische **Datenunabhängigkeit**: Anwendungen müssen nicht geändert werden, wenn sich Speicherung oder Tabellenstruktur ändern (siehe [Schemaebenen](/de/databases/schema/#schemaebenen)).

Kein verbreitetes Produkt erfüllt alle Regeln vollständig, sie dienen aber bis heute als Maßstab.

## SQL

**SQL** (_Structured Query Language_) ist die Sprache relationaler Datenbanken. Sie wurde in den 1970er-Jahren bei IBM entwickelt und ist seit 1986 als ANSI- und seit 1987 als ISO-Standard (ISO/IEC 9075) festgelegt. Die aktuelle Fassung ist SQL:2023. SQL ist **deklarativ**: Man beschreibt das gewünschte Ergebnis, nicht den Weg dorthin. Die Befehle werden in Gruppen eingeteilt:

| Gruppe                                    | Befehle                                   | Seite                                                      |
| ----------------------------------------- | ----------------------------------------- | ---------------------------------------------------------- |
| **DDL** (_Data Definition Language_)      | `CREATE`, `ALTER`, `DROP`, `TRUNCATE`     | [SQL: Daten definieren und ändern](/de/databases/sql-ddl-dml/) |
| **DML** (_Data Manipulation Language_)    | `INSERT`, `UPDATE`, `DELETE`, `MERGE`     | [SQL: Daten definieren und ändern](/de/databases/sql-ddl-dml/) |
| **DQL** (_Data Query Language_)           | `SELECT`                                  | [SQL-Abfragen](/de/databases/sql-queries/)                 |
| **DCL** (_Data Control Language_)         | `GRANT`, `REVOKE`                         | [Datenbanksicherheit](/de/databases/database-security/)    |
| **TCL** (_Transaction Control Language_)  | `BEGIN`, `COMMIT`, `ROLLBACK`, `SAVEPOINT` | [Transaktionen](/de/databases/transactions/)              |

Häufig wird DQL zur DML gezählt. Die theoretische Grundlage von `SELECT` ist die [relationale Algebra](/de/databases/relational-algebra/).

## Vorteile und Nachteile

| Vorteile                                                                                   | Nachteile                                                                                        |
| ------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------ |
| einfaches, mathematisch fundiertes Datenmodell                                             | starres Schema: Strukturänderungen an großen Tabellen sind aufwendig                             |
| wenig Redundanz durch [Normalisierung](/de/databases/normalisation/)                       | zusammengehörige Daten sind auf viele Tabellen verteilt und müssen mit Joins zusammengesetzt werden |
| hohe Konsistenz durch Constraints und [Transaktionen](/de/databases/transactions/)         | horizontale Skalierung über viele Server ist schwierig, weil Joins und Transaktionen über Servergrenzen teuer sind |
| standardisierte, mächtige Abfragesprache SQL                                               | hierarchische oder stark vernetzte Daten (Bäume, Graphen) passen schlecht in Tabellen           |
| ausgereifte Produkte, Werkzeuge und viel Fachwissen                                        | Objekte im Programm und Tabellen passen nicht direkt zusammen (_Object-relational impedance mismatch_), was ORMs wie [Entity Framework](/de/databases/database-access/#entity-framework-core) ausgleichen |

Für sehr große, verteilte oder schwach strukturierte Datenmengen gibt es deshalb [NoSQL-Datenbanken](/de/databases/nosql/). In den meisten Geschäftsanwendungen ist eine relationale Datenbank aber die richtige erste Wahl.

## Produkte

| Produkt                  | Lizenz                      | Besonderheiten                                                                                   |
| ------------------------ | --------------------------- | ------------------------------------------------------------------------------------------------ |
| **PostgreSQL**           | Open Source (PostgreSQL-Lizenz) | sehr standardkonform, objektrelational, viele Datentypen (JSON, Arrays, Geodaten mit PostGIS), erweiterbar |
| **MySQL**                | Open Source (GPL) und kommerziell, gehört zu Oracle | weit verbreitet in Webanwendungen, Teil des LAMP-Stacks (Linux, Apache, MySQL, PHP) |
| **MariaDB**              | Open Source (GPL)           | 2009 von MySQL-Gründer Michael Widenius abgespaltener Fork, weitgehend kompatibel zu MySQL       |
| **Microsoft SQL Server** | kommerziell, kostenlose Express- und Developer-Edition | SQL-Dialekt T-SQL, sehr gute Integration in .NET und Entity Framework     |
| **Oracle Database**      | kommerziell                 | in großen Unternehmen verbreitet, prozedurale Erweiterung PL/SQL                                  |
| **SQLite**               | gemeinfrei                  | eingebettete Bibliothek ohne Server, ganze Datenbank in einer Datei, in jedem Smartphone und Browser |
| **IBM Db2**              | kommerziell                 | Nachfolger des ersten SQL-Systems, vor allem auf Großrechnern                                    |

Die Beispiele auf diesen Seiten verwenden PostgreSQL-Syntax, die dem Standard sehr nahe kommt. Abweichungen der anderen Systeme werden dort erwähnt, wo sie häufig vorkommen.
