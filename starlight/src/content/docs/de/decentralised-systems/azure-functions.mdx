Azure Functions sind Serverless Computing in Microsoft Azure. Serverless Computing ist ein eher irreführender Begriff. Serverless bedeutet in diesem Zusammenhang einfach, dass Ressourcen `on demand` ein- und ausgeschaltet werden. Wenn also momentan viele Anfragen auf deine Website eintreffen, werden im Hintergrund mehrere Instanzen gestartet. Logischerweise werden auch hier Server verwendet, um diese Anfragen entgegenzunehmen. Allerdings bekommt der Developer nichts davon mit, damit er/sie sich mehr auf die Applikation selbst konzentrieren kann.

Im **Verbrauchstarif** (_Consumption Plan_) bezahlt man nur für die tatsächliche Ausführungszeit der Funktionen. Dafür ist die Laufzeit einer einzelnen Ausführung begrenzt (standardmäßig 5, maximal 10 Minuten) und nach längerer Inaktivität kann der erste Aufruf etwas länger dauern (_Cold Start_).

:::note
Die Beispiele auf dieser Seite verwenden das **isolierte Workermodell** (_isolated worker model_), bei dem die Funktionen in einem eigenen .NET-Prozess laufen. Das ältere In-Process-Modell wird von Microsoft nur noch bis November 2026 unterstützt. Kurzschreibweisen, wie zum Beispiel `AzureWebJobsStorage`, sind in der Datei `local.settings.json` bzw. in den Einstellungen der Function App definiert.
:::

Eine Azure Function, welche mittels [`NCRONTAB` expression](https://learn.microsoft.com/en-us/azure/azure-functions/functions-bindings-timer?tabs=python-v2%2Cisolated-process%2Cnodejs-v4&pivots=programming-language-csharp#ncrontab-expressions) alle 10 Sekunden getriggert wird, sieht zum Beispiel so aus:

```csharp
public class RecurringEvent(ILogger<RecurringEvent> logger)
{
    [Function("MyTimerTrigger")]
    public void Run([TimerTrigger("*/10 * * * * *")] TimerInfo myTimer)
    {
        logger.LogInformation("Function executed at: {Time}", DateTime.Now);
    }
}
```

## Input Trigger

Jede Azure Function ist eine einfache Funktion in C# oder [anderen Programmiersprachen](https://learn.microsoft.com/de-de/azure/azure-functions/supported-languages?tabs=isolated-process%2Cv4&pivots=programming-language-csharp). Dabei benötigt jede AF (Azure Function) genau einen Trigger, der festlegt, wann sie ausgeführt werden soll. Es gibt viele verschiedene Arten von Triggern:

| Azure Function Trigger                                                                                                    |
| ------------------------------------------------------------------------------------------------------------------------- |
| HTTP Trigger (Ausführung bei HTTP Request)                                                                                |
| Timer Trigger (Ausführung in Intervallen)                                                                                 |
| Queue Trigger (Ausführung bei neuer Message in [Queue Storage](/de/decentralised-systems/storage-account/#queue-storage)) |
| Blob Trigger (Ausführung bei Dateiupload in [Blob Storage](/de/decentralised-systems/storage-account/#blob-storage))      |
| Cosmos DB Trigger                                                                                                         |
| Event Grid Trigger                                                                                                        |
| Event Hub Trigger                                                                                                         |
| Service Bus Trigger                                                                                                       |

Die folgenden Beispiele sind Methoden innerhalb einer Klasse, die wie oben einen `ILogger` über den Konstruktor erhält.

### Timer Trigger

Wenn eine AF zum Beispiel alle 5 Minuten ausgeführt werden soll, kann man diese Function verwenden. Das Format lautet `{Sekunde} {Minute} {Stunde} {Tag} {Monat} {Wochentag}`:

```csharp
[Function("MyTimerTrigger")]
public void Run([TimerTrigger("0 */5 * * * *")] TimerInfo myTimer)
{
    logger.LogInformation("Function executed at: {Time}", DateTime.Now);
}
```

### HTTP Trigger

Wenn eine AF zum Beispiel bei einem HTTP Request auf die Route `/api/trueberryless` ausgeführt werden soll, kann man diese Function verwenden (mit dem Paket `Microsoft.Azure.Functions.Worker.Extensions.Http.AspNetCore`):

```csharp
[Function("MyHttpTrigger")]
public IActionResult Run(
    [HttpTrigger(AuthorizationLevel.Function, "get", Route = "trueberryless")] HttpRequest req)
{
    logger.LogInformation("C# HTTP trigger function processed a request.");
    return new OkObjectResult("Hallo trueberryless!");
}
```

Mit `AuthorizationLevel.Function` muss beim Aufruf ein Funktionsschlüssel (`?code=...`) mitgeschickt werden, mit `AuthorizationLevel.Anonymous` ist die Funktion öffentlich erreichbar.

### Blob Trigger

Bei jeder neuen Datei im Container wird diese AF ausgeführt:

```csharp
[Function("MyBlobTrigger")]
public void Run(
    [BlobTrigger("blobs/{name}", Connection = "AzureWebJobsStorage")] Stream stream,
    string name)
{
    logger.LogInformation("C# Blob trigger function processed the file {Name}.", name);
}
```

### Queue Trigger

Bei jeder neuen Message in der Queue wird die Function getriggert. Jede Message wird dabei genau von einem Empfänger verarbeitet. Sollen Nachrichten an mehrere Empfänger verteilt werden (Publish/Subscribe), verwendet man stattdessen die **Topics** von Azure Service Bus. Eine Nachricht an ein Topic wird an alle Abonnenten zugestellt.

```csharp
[Function("MyQueueTrigger")]
public void Run(
    [QueueTrigger("messages", Connection = "AzureWebJobsStorage")] string message)
{
    logger.LogInformation("C# Queue trigger function processed a message: {Message}", message);
}
```

Schlägt die Verarbeitung einer Nachricht mehrmals fehl (standardmäßig fünfmal), wird sie in eine eigene Queue mit der Endung `-poison` verschoben, damit sie später untersucht werden kann.

## Input Binding

Wenn in der Azure Function Zugriff auf einen Storage Account benötigt wird, kann dies relativ einfach mittels Input Bindings umgesetzt werden. Das folgende Beispiel liest alle Bäume der Partition `tree` aus der Tabelle `TreeTable` und gibt sie zurück:

```csharp
[Function("MyInputBinding")]
public IActionResult Run(
    [HttpTrigger(AuthorizationLevel.Function, "get")] HttpRequest req,
    [TableInput("TreeTable", "tree")] IEnumerable<TreeTable> trees)
{
    return new OkObjectResult(trees);
}

public class TreeTable : Azure.Data.Tables.ITableEntity
{
    public double TreeHeight { get; set; }
    public string TreeType { get; set; }

    public string PartitionKey { get; set; }
    public string RowKey { get; set; }
    public DateTimeOffset? Timestamp { get; set; }
    public ETag ETag { get; set; }
}
```

Statt einer fertigen Liste kann man sich auch einen `TableClient` übergeben lassen (`[TableInput("TreeTable")] TableClient tableClient`), um beliebige Abfragen oder Änderungen selbst durchzuführen.

## Output Binding

Wenn du als Rückgabewert Daten in einen Storage Account schreiben willst, eignet sich hierfür das Output Binding. Das folgende Beispiel erzeugt für jedes hochgeladene Bild automatisch ein Vorschaubild mit der Bibliothek ImageSharp:

```csharp
[Function("MyOutputBinding")]
[BlobOutput("thumbnails/{name}", Connection = "AzureWebJobsStorage")]
public async Task<byte[]> Run(
    [BlobTrigger("images/{name}", Connection = "AzureWebJobsStorage")] Stream imageStream,
    string name)
{
    using var image = await SixLabors.ImageSharp.Image.LoadAsync(imageStream);
    var newWidth = 300;
    var newHeight = 200;

    image.Mutate(x => x.Resize(new ResizeOptions
    {
        Size = new Size(newWidth, newHeight),
        Mode = ResizeMode.Max
    }));

    using var thumbnailStream = new MemoryStream();
    await image.SaveAsync(thumbnailStream, new JpegEncoder());
    return thumbnailStream.ToArray();
}
```

Auf dieselbe Weise gibt es Output Bindings für Tabellen (`[TableOutput]`) und Queues (`[QueueOutput]`). Sollen mehrere Ausgaben gleichzeitig geschrieben werden, gibt man eine eigene Klasse zurück, deren Properties jeweils mit einem Output-Binding-Attribut versehen sind.
